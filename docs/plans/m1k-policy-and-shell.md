## Delegated decisions

Taken under the owner's standing instruction; each can be reverted.

- D1. **One reader for version 1.** `internal/policy` decodes every section of ADR-0032 §1: types as shown, `null` is the default, every path key (`trust.*`, `shell.roots`, `gradle.sidecarJavaHome`, `tools.*`) absolute or the file is invalid, `devices.allowlist` non-empty strings; unknown keys, top-level and inside known sections, kept on every rewrite and ignored. One size-and-mtime snapshot answers trust, shell and devices per check (ADR-0031 §4; ADR-0032 §6); the tool keys are read once at daemon start from the same decode. **An invalid file** (ADR-0032 §4) trusts nothing (`WORKSPACE_UNTRUSTED`, as now), keeps `shell.exec` off (`POLICY_SHELL_DISABLED`), admits no physical device (`DEVICE_NOT_ALLOWED`; emulators unaffected) and uses no tool key; each error's `cause` names the file and the parse error. `system.health` gains `config {path, state: missing | ok | invalid, error?, toolKeys: missing | ok | invalid}` (`toolKeys` as read at start). The daemon holds one `Policy`.
- D2. **`policy.get {}`** → `{path, state, error?, trust {roots, prefixes}, devices {allowPhysical, allowlist}, shell {enabled, roots}}`: the policy sections as written in the file, defaults when it is missing or invalid. It never fails on a bad file: the UI must be able to show the problem. Not untrusted. Errors: none of its own.
- D3. **`policy.update`.** Its params are the patch, restricted: `{trust?, devices?, shell?}`, each a section object or `null`, each known key a value or `null`; the schema closes every object (`additionalProperties: false`), so `{"shell": {"enable": true}}` or `{"gradle": …}` is `REQUEST_INVALID_PARAMS` at `Start` rather than a silent no-op (keys already in the file are still kept). Under the exclusive `flock` on `config.json.lock`: re-read, apply RFC 7386 to the sections, canonicalise every path entry as `droidyard trust` does (a relative one → `REQUEST_INVALID_PARAMS` naming the key, file untouched), validate with D1's rules, write atomically, drop the cache. An empty patch writes nothing. A file that does not parse or is newer → `POLICY_CONFIG_UNUSABLE`, untouched (ADR-0031 §3); a write failure → the same code, `cause` the OS error. Result: D2's shape after the write. **Arrays are replaced whole** (RFC 7386): to add a root the caller sends the list. A `droidyard trust` landing between a UI's `get` and an `update` that sends `trust.roots` is lost; a revision token would fix it and is not in ADR-0032. **The owner should see it.** No `droidyard policy` subcommand: the CLI channel is `droidyard call policy.update --params …` (ADR-0015 §6).
- D4. **`shell.exec`'s gate**, in its `Authorize` hook, re-checked before the handler (ADR-0015 §2, ADR-0020): first the shell policy (`shell.enabled`, or the canonical root equal to or under a `shell.roots` entry at a path-component boundary, `trustedBy`'s rule), else `POLICY_SHELL_DISABLED` naming the root, nextStep "ask the user to enable shell.exec for this project (`shell.roots` in <config path>), or use a modelled capability"; then trust, `WORKSPACE_UNTRUSTED` as `project.*` (ADR-0032 §2). Shell first: it is the capability's own gate (ADR-0015 §7). `system.capabilities` reports it available whatever the policy: availability is about tools, and the list stays stable.
- D5. **`shell.exec`'s run.** Params `{command, timeoutMs?}`: `command` 1–8192 bytes, no NUL; `timeoutMs` 1000–600000, default 60000. `/bin/sh -c <command>`, cwd the canonical root, the daemon's environment, stdin `/dev/null`, spawned by `SpawnRecorded` with kind `shell-command`: its own group, and **no `Pdeathsig`** for this kind (on Linux it would kill only the leader when the daemon dies, and `Reconcile`, which keys on a live leader, would then drop the record and leave the rest of the group running; without it the leader survives the daemon on both OSes and reconciliation reaps the group). The call ends when the shell exits, at the timeout, or on cancel (`operation.cancel`, `workspace.close`'s cancel, daemon shutdown). A goroutine in `Wait` reaps the shell as soon as it exits; then, at every end, the group gets SIGTERM if `kill(-pgid, 0)` still finds a member, SIGKILL after 2 s, and is polled gone for at most 1 s. The record goes at the reap, as `Recorded.Wait` does (once the leader is reaped, `Reconcile` would drop it anyway). So **a command's background processes end with the call** (`process-lifecycle.md`: no orphans); a process that leaves the group (`setsid`/`setpgid`: a forked adb server, Gradle's daemon) survives by design. Pipes are not read past that point (`WaitDelay` 1 s), so a background child holding stdout cannot hold the call. The record is written once the shell has started, so if it cannot be written the group is killed and the call fails `SHELL_EXEC_FAILED`, whose `cause` says the command had started and may have had effects. The group kill departs from m1e R8's pid-only kill of adb clients: it is safe for the same reason 1i D9's reconciliation is, adb puts its server in a group of its own (Rests on, step 2).
- D6. **`shell.exec`'s result**: `{exitCode?, signal?, timedOut, durationMs, stdout, stderr, stdoutBytes, stderrBytes, stdoutRef?, stderrRef?, truncated}`. `stdout`/`stderr` are each stream's last 16 KiB, invalid UTF-8 replaced, tagged untrusted (a command can print device text). A stream over 16 KiB is also kept as an ephemeral text artifact of its first 4 MiB, with a closing marker naming the bytes dropped (capped while capturing, as the build console is; `truncated`), carrying the call's mark (ADR-0015 §1); the inline tail already gives the end. A non-zero exit and a timeout are **completed** results (`timedOut: true`, the partial output): like a failed build, they are information. A cancel is `cancelled`, no result (ADR-0020). It fails only with `POLICY_SHELL_DISABLED`, `WORKSPACE_UNTRUSTED`, `SHELL_EXEC_FAILED` (the shell cannot start, the root is gone, the record cannot be written) and `REQUEST_INVALID_PARAMS`. No `Resource` key: commands run in parallel with each other and with builds, as in the user's own terminal. The description says it is off unless the user enables it, runs `/bin/sh -c` in the project root with the user's full rights (droidyard's own configuration included, Q1) and must never be used to change droidyard's configuration or trust, kills background processes when it ends, returns tails inline and the rest by reference, and that modelled capabilities come first; `POLICY_SHELL_DISABLED`'s message says the same to the human who reads it.
- D7. **Device policy.** `device.ADB` takes a policy (an interface in `device`, implemented by `*policy.Policy`; none means emulators only, so existing tests stand) consulted by the hook and by the listing: a device of kind `physical` is admitted iff `allowPhysical` and its exact serial is in `allowlist`. Listings, and `DEVICE_NOT_FOUND`'s `online` candidates, show admitted devices only. `DEVICE_NOT_ALLOWED`'s `cause` says which condition failed (`allowPhysical` false, not in `allowlist`, or the invalid file by name); nextStep "use an emulator serial from device.list, or ask the user to admit <serial> in the droidyard configuration (`devices.allowPhysical` and `devices.allowlist`)". Re-read per call (D1). `emulator.stop` of an admitted physical serial passes the hook and gets `EMULATOR_NOT_AN_EMULATOR`.
- D8. **Tool keys, at daemon start.** `gradle.sidecarJavaHome`: the first JVM candidate, source `gradle.sidecarJavaHome`, validated like every candidate, rejected → the next (`gradle.md` §Sidecar JVM discovery). `tools.adb`: the first adb candidate (R3), source `tools.adb`; not executable → **fail closed**, nothing after it tried, as `ADB` (m1e Q6: falling through could pick an adb that restarts the shared server). `tools.emulator`: the first launcher candidate, source `tools.emulator`; not executable → rejected, the next (its absence affects only its subsystem, `emulator.md`). The launcher derived from adb's location uses adb as resolved. Each "Tried:" text names the key and the file. **An invalid file at start** (ADR-0032 §4, "reported by every capability the bad file affects"): each of the three resolutions carries a rejected entry `{candidate: <config path>, source: <key>, reason: "the configuration file is invalid (<error>); its tool keys were not read"}`, so `system.health`, `system.capabilities`' unavailable reasons and every not-found error show it, and a resolution that still succeeds through another source still lists it; adb then falls through to `ADB`, the SDK and `PATH` (ADR-0032 §4: the file's keys are unused, not adb refused). When `tools.adb` wins while `ADB` is set, adb's rejected list gains `{candidate: $ADB, source: ADB, reason: "overridden by tools.adb"}`, so `system.health` shows the override (R3). Host SDK discovery (`sdk.md` §Host SDK) is unchanged.
- D9. **Below the floor** (ADR-0018 rule 3, R4). Gradle 7.3–7.x: `BUILD_GRADLE_UNSUPPORTED` naming floor, version and the hatch ("set `gradle.allowBelowFloor: true` in <config path> and restart droidyard"), unless the key was set at start; then the connection opens with profile `conservative` and every build result and record says `validation: unsupported`. Both are recordings rather than new mechanisms: no step changes when they are answered as drafted. The main session may apply them under the owner's standing instruction (`Delegated`); the owner can revert either.

### Q1. Enabling `shell.exec` lets the agent change droidyard's policy

- Blocks: step 2 (its description, D6) and the close (D10); the plan's claim that policy is human-only.
- The documents say: ADR-0032 Consequences, "An agent still cannot change policy: `policy.update` is human-only, and `shell.exec` needs a human to enable it"; ADR-0015 §6, the residual-risk defence is "that our agent-facing surface offers no path to it"; `mcp-tool-surface.md` §Server instructions, "Policy … is changed by the user, not through this server". Once a root is enabled, `shell.exec` runs as the user: `droidyard trust /`, `droidyard call policy.update` (client kind `cli` passes the audience check, `capability/operation.go` `prepare`) and an edit of `config.json` all work from it, so the agent can enable the shell everywhere, trust any root and admit physical devices.
- Draft decision: an `Amended:` line on ADR-0032 (Consequences) and ADR-0015 §6, labelled `Delegated`: enabling `shell.exec`, globally or for one root, gives the agent the user account's full reach, not confined to that root, droidyard's configuration and trust included; for that case it replaces ADR-0015 §6's "the defence is that our agent-facing surface offers no path to it", which no longer holds once the shell is on. No fence is attempted: a same-uid process can always write the file. The human is told before enabling: the `shell.exec` description and `POLICY_SHELL_DISABLED`'s message say so (D6), and `capability-api.md` at the close (D10); the description also instructs the agent never to change droidyard's configuration or trust through it (ADR-0015's "marking, instructions and policy"). Rejected alternatives: a marker variable in the command's environment that `droidyard trust` and `droidyard call` refuse (unset, or bypassed by editing the file: a false fence); a sandbox denying writes to the configuration directory (macOS `sandbox-exec`, deprecated; Linux Landlock), platform-specific and a project of its own, with no MVP acceptance item needing it.

### Q2. What configuration version 1 defers, and the two precedence readings

- Blocks: §Scope's deferral row; step 6 (R3) and step 7 (R4) rest on ADR readings that should be recorded in an ADR before code depends on them.
- The documents say: `http-websocket.md` §Security baseline rule 1, the port "becomes configurable when the configuration file exists (Phase 1)"; `gradle.md` §Environment and JVM, "Environment source is explicit: inherit, shell-probed, or none"; `process-lifecycle.md` §Idle shutdown, "a configurable idle period". ADR-0032 Consequences defer only timeouts, yet claim "Every config key the documents promised now has a defined place". R3 reverses `adb-device.md` §adb resolution and degradation's order; R4 departs from ADR-0018 rule 3's "per-workspace configuration".
- Draft decision: one `Amended:` line on ADR-0032, labelled `Delegated`: version 1 defers the HTTP port (7317 with its ephemeral fallback stays), the environment source (inherit), idle periods and build retention (`gradle.md` §Persistence, "Configurable"), besides timeouts, to a later version under new sections; `tools.adb` precedes the `ADB` variable (R3); `gradle.allowBelowFloor` is one global key read at start (R4); and the Alternatives' claim that Merge Patch under the lock avoids losing a concurrent `droidyard trust` holds only for a patch that does not carry `trust.roots` (D3). And an `Amended:` line on ADR-0018 rule 3 pointing at ADR-0032. Written before step 1. Rejected alternative: add an `http.port` key in 1k; it serves no Phase 1 acceptance item, and the fallback already handles a taken port.
