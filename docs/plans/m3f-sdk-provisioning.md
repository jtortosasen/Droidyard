## Acceptance

- [ ] A1. **Listing**: `sdk.packages` returns the installed packages (every repository package whose directory holds `package.xml` or `source.properties`, plus the six fixed locations' packages) and the available ones of the stable channel for this host (system images of its ABI), each with version, the size of this host's archive, its licence (id and sha1) and whether it is accepted, dependencies and whether an update is available; it is bounded, says when the repository could not be read, and still lists what is installed then. Source: sdk.md §Provisioning; Q3. Proven by: step 2, step 10.
- [ ] A2. **Consent**: a licence is accepted only by `sdk.acceptLicense {id, sha1}` from a human client, with the hash of a text the repository serves now for that id, the hash being sdklib's (`sha1` of the text after `TrimStringAdapter`'s four steps, ADR-0130 §3); it writes that hash into `<root>/licenses/<id>`, the line AGP, Android Studio and the classic tools compare, and a line in `daemon.log`; MCP sessions are refused it; no other code path writes `licenses/`; no `sdkmanager` or Android CLI ever runs, and `avdmanager` never reads consent (stdin `/dev/null`, or a fixed `no`). Source: sdk.md §Provisioning; ADR-0015 §6; Q2; ADR-0130 §1, §3. Proven by: step 3, step 4, step 6, step 10.
- [ ] A3. **Install, update, uninstall**: `sdk.install` installs the ids not installed, updates an installed id that has a newer revision, does nothing for one at the latest, and updates a dependency below the revision a package requires; it refuses before any download when a licence (id and text) of the packages or their dependencies is pending (naming them), when an id is unknown, when the disk lacks the archives' total, or when a package it would replace is in use (A10). Then Droidyard itself, dependencies first, downloads each archive over HTTPS from the repository's host, checks its size and sha1 while streaming, refuses before unpacking when the disk lacks its uncompressed size or an entry escapes, is not a regular file or directory, or passes the bounds, writes `package.xml` in the form the classic tool writes, and moves the package into place last; with progress, a time bound and cancellation; nothing reaches a package's final path unverified or half-written, and an interrupted install never lists a package as installed. What it installs is read as installed by the classic `sdkmanager`, by `avdmanager` and by AGP. `sdk.uninstall` (human) refuses a package in use, removes the others and reports what it freed. Source: sdk.md §Provisioning; ADR-0020; ADR-0130 §1, §2; Q4, Q6, Q8. Proven by: step 4, step 5, step 10.
- [ ] A4. **From nothing**: on a host with no SDK, `sdk.install` creates the target root Q5 names and installs into it like any other package, needing neither a JVM nor `cmdline-tools`; `cmdline-tools` is an ordinary package, needed only for `avdmanager`. Source: owner; Q5; ADR-0130 §4. Proven by: step 4, step 10.
- [ ] A5. **AVDs**: `sdk.profiles` lists the device profiles; `emulator.create {avd, profile, systemImage, settings?}` creates an AVD the launcher then lists, refusing a name present in any AVD home, a missing image (naming `sdk.install`) and an unknown profile; `emulator.delete` (human) refuses a running AVD (Q7's check) and a name in two homes, and removes it otherwise. Source: emulator.md §Capabilities; Q7. Proven by: step 6, step 10.

Source: process-lifecycle.md; ADR-0021 §Pid records; Q6; ADR-0130 §1, §5. Proven by: step 4, step 6, step 10.

Candidates are the processes whose executable lies under the SDK root or whose arguments name it, and those whose executable's base name is `java`, `adb`, `emulator`, `studio` or begins `qemu-system-`: the processes that run SDK code or load SDK files; a file held open by a process outside that set is not seen (a register row). ### 2. The repository and `sdk.packages`

- Builds: in `internal/domain/sdk`:
  - `repository.go`: base `https://dl.google.com/android/repository/` (a constant; `Options.RepositoryBase` only for tests, an `httptest` TLS server). It reads `repository2-3.xml` and the system-image lists `addons_list-5.xml` names whose URL is relative to that base (any other is ignored with a warning); HTTPS only, no redirect off the host, each body capped at 16 MiB while read, at most 32 lists and 20,000 packages, 25 s for the whole fetch. Decoded with `encoding/xml` into structs holding only step 1 (b)'s elements. Kept in memory for an hour; `refresh` refetches; a failed refetch keeps the old copy and says so. Each archive's `url` (a bare file name, step 1 (b)) is resolved against its own list's directory (`sys-img/android/x.zip` for a list under `sys-img/android/`); an absolute URL, or one that resolves off the base's host or outside the base path, drops that archive with a warning.

## Design questions

Delegated (owner, 2026-10-25: "apply the recommended option"; and "metelo en 3f" for Q8 and Q9's scope): the main session writes ADR-0129 with Q1–Q9 as recommended and lands it with this plan's commit; step 1 may run first, and if it contradicts a draft, the steps it touches are redrafted under Changes before they start.

- **Q1. Which capabilities are agent tools** (row 360). The documents say: mcp.md left it open; ADR-0015 §6 and ADR-0108 §1 keep consent and policy human; ADR-0060 §2 defines audience `human`; ADR-0036 budgets the list. Recommended: MCP gets what closes an agent's loop when a build or boot lacks a piece: `sdk.packages`, `sdk.install` (install or update, only packages whose licences a person accepted, never one in use), `sdk.profiles`, `emulator.create` (with settings); human-only: `sdk.licenses`, `sdk.acceptLicense` (consent), `sdk.uninstall`, `emulator.delete` (they remove host-wide state that other projects and the user rely on, with no undo), and `emulator.configure` (editing an AVD the user may rely on; an agent sets what it needs at creation). About 4 KB more on `tools/list`, held by ADR-0060 §4's rule. Rejected: **everything human-only**: an agent that hits "platform android-35 is missing" could only hand the user a command, which the owner's brief rules out; **everything on MCP**: the agent would consent for the user and delete what it did not make; **in `--tools core`**: provisioning is off the golden path.
- **Q2. How licences are accepted** (row 447). The documents say: sdk.md, never on the user's behalf, only on an explicit call; mcp.md, elicitation as the candidate, never a policy channel; ADR-0015 §Alternatives considered rejected elicitation-gated policy. Recommended: a licence is (id, sha1), since one id can have several texts across lists; `sdk.acceptLicense {id, sha1}`, audience human, with the sha1 of the text the person was shown, refused unless the repository serves that text now; it writes the hash into `<root>/licenses/<id>`, the file `sdkmanager`, AGP and Android Studio read; its audit is the operation (client kind, Activity), one `daemon.log` line and the file itself; its own scheduler key, so it never waits on an install. The tools never get consent: stdin `/dev/null`. An agent meets `SDK_LICENSE_NOT_ACCEPTED` naming the person's step. The residual risk is ADR-0015 §6's: an agent's own shell can run `droidyard sdk accept-license`, as it can run `policy update`. Rejected: **elicitation** (uneven support, an auto-approving client); **answering `sdkmanager --licenses` prompts** (kept only as step 1 (a)'s fallback writer); **a durable audit file in the state directory** (ADR-0099 §Alternatives considered gives the reason); **accepting by id without a hash**.
  - 2026-10-26, ADR-0130 §3: the sha1 is sdklib's hash of the `TrimStringAdapter`-normalised text (step 1 (a)); no `sdkmanager` runs, so "the tools never get consent" now concerns `avdmanager` alone, and the `--licenses` fallback is moot.
- **Q3. Listing modelled from the repository** (row 448). Recommended: Go reads Google's repository XML (a fixed HTTPS base, bounded, cached an hour in memory), modelling packages, sizes, licences, dependencies and available updates; `sdkmanager --list` is not parsed; installed state is read for every repository id at its id-as-path directory (`cmdline-tools;latest` at the highest revision under `cmdline-tools/*`). Text from the repository (display names, licence texts) is tagged untrusted (ADR-0015 §1 extended); ids and versions are validated by pattern. Rejected: **`sdkmanager --list` verbatim** (no sizes, no licence texts, a JVM start per listing, no contract); **modelled from `--list`**; **untagged repository text**.
- **Q4. Who writes what** (ADR-0005). The documents say: ADR-0005 decides on the platform tools and rejects Android CLI; sdk.md assumes a JDK. Recommended: Droidyard owns the flow (what to install or update, consent, in use, checks, progress, cancel, results) and drives `sdkmanager` and `avdmanager` for every write inside the SDK and for creating and deleting AVDs, so `package.xml` files, dependency handling and the AVD's first `config.ini` are the ones other Android tools write; Go writes only the licence file (Q2), the bootstrap (Q5) and the allowlisted hardware keys of an existing `config.ini` (Q9), where the tools offer nothing. Rejected: **a package manager in Go** (it reimplements `sdklib`'s formats that AGP and Studio parse); **Android CLI** (ADR-0005); **asking the user to run the tools**.
  - 2026-10-26, superseded by ADR-0130 §1, §5: step 1 found today's `sdkmanager` is Android CLI and accepts licences itself, so Droidyard installs, updates and removes packages in Go, held to the formats by a golden `package.xml`, the classic `sdkmanager`, `avdmanager` and AGP (step 4, step 10); `avdmanager` stays for AVDs.
- **Q5. Setting up an SDK from nothing.** Recommended: `sdk.install` sets up the tools when none exist, into the host SDK if found, else `ANDROID_HOME`, else `ANDROID_SDK_ROOT`, else the per-OS default; a target that exists, is not empty and is not an SDK is refused; the archive from the repository over HTTPS, size and sha1 checked while streaming, unpacked inside a temporary directory under the root with escapes refused, renamed into place last, its licence accepted first. No separate capability. Rejected: **`sdk.setup`**; **a pinned download URL**; **the configuration's `sdk.root` key** (unspecified, plan m1e R5).
  - 2026-10-26, ADR-0130 §4: no bootstrap; `sdk.install` creates the target root and installs into it like any package, the download rules above now applying to every package; `cmdline-tools` is needed only for `avdmanager`.
- **Q6. Process lifetime of the tools.** Recommended: kind `sdk-tool`, recorded, its own session and group, the group ended SIGTERM then SIGKILL at every end of the call and after the tool exits, no death signal, the next daemon's Reconcile ending a survivor's group; bounds of 60 min and 10 min silent for install, 5 min otherwise (working defaults); one `sdk:<root>` key serialising installs and uninstalls on a root; an AVD's create, edit and delete on `emulator.boot`. Short `avdmanager` runs are recorded too, beyond ADR-0021 §Pid records, whose "short per-operation commands are not recorded": one runner, and a JVM can hang. `lsof` (step 5) is a bounded per-operation client, not recorded. Rejected: **unrecorded tool runs**; **a death signal** (it reaches the leader only; the `git-write` precedent).
  - 2026-10-26, ADR-0130 §5: kind `sdk-tool` and the runner serve `avdmanager` only (step 6); installs and uninstalls run in the daemon, spawn nothing, end with the call's context, and keep the 60 min and 10 min bounds (10 min without a byte).
- **Q7. Where an AVD is created, and when it is running** (rows 214, 219). Recommended: create sets `ANDROID_AVD_HOME` for `avdmanager` to the launcher's first AVD directory (step 1 (d) fixes the order); a name present in any home is refused; delete and edit refuse a name in two homes and a running AVD: running under any adb server, known by this daemon's adb listing, an emulator process whose arguments name it, a candidate process (Q8) holding a file open in its `.avd` directory, or step 1 (d)'s lock; any doubt is running. Rejected: **`avdmanager`'s own default**; **deleting the first match**; **this daemon's adb listing alone**.
  - 2026-10-26, step 1 (d): the launcher lists one directory, the first existing of `ANDROID_AVD_HOME`, `ANDROID_SDK_HOME/.android/avd`, `HOME/.android/avd`; a running emulator's lock was not observed, so it counts only through the open-file check (Q10, step 6).
- **Q8. Updates, never of a package in use** (owner, 2026-10-25: updates in scope, by a person and by an agent at the planner's call). The documents say: nothing. Recommended: **`sdk.install` updates**: an installed id with a newer revision is updated, one at the latest is left alone, and a dependency below the revision a package requires is updated as part of the install (named on `sdkmanager`'s argv); agents and people alike, under the same licence rule. `sdk.install` becomes destructive (an update does not keep the older revision), a hint clients show as an approval. **In use**: before any update or uninstall, every package to be replaced or removed is checked by A10's rule: an executable running from inside it, by any process of the user (`kern.procargs2`, `/proc`); a file open inside it, held by a candidate process (`/usr/sbin/lsof`), the candidates being the processes that run SDK code or load SDK files (executable under the root or arguments naming it; `java`, `adb`, `emulator`, `studio`, `qemu-system-*`); or a Droidyard boot or build in flight that needs it. The candidate set bounds `lsof`'s cost (output and time over every process of the user are unbounded) and lets a missing live candidate count as a doubt; a non-candidate holding an SDK file open is not seen (a register row). Any doubt counts as in use; zombies and gone processes are skipped. `SDK_PACKAGE_IN_USE` names what uses each package; its nextStep asks the user to stop it, never the agent (stopping the adb server or an emulator drops other sessions' devices and streams, mcp.md §Annotations). `SDK_UPDATE_NEEDED` is dropped. Rejected: **a separate `sdk.update`**: one more tool and a second path to the same `sdkmanager` call; it wins if the destructive hint on every install proves noisy; **updates human-only**: the owner allowed agents, consent is the licence's, and the in-use check guards the harm; **in use by process names (`ps`)**: a 16-character name misses `qemu-system-aarch64-headless`, and an adb started from another SDK has the same name; **`lsof` over every process of the user**: unbounded; **refusing every update while any emulator or adb server runs**: it refuses updates of packages nothing uses.
  - 2026-10-26, step 1 (f): two setuid `login` processes, unreadable, run in every terminal session, so §8's "any unreadable live process is a doubt" would refuse every update; the rule that skips them is Q10. Updates are now Droidyard's own replace (ADR-0130 §1), not `sdkmanager`'s argv.
- **Q9. AVD hardware settings** (owner, 2026-10-25: in scope, at creation and as an edit). The documents say: emulator.md §Capabilities, "advanced settings exposed with sensible defaults, not hidden"; §Flags and configuration, memory configuration "is the AVD's business". Recommended: typed settings, not keys: display name, RAM, VM heap, internal storage, SD card (at creation, through `avdmanager --sdcard`), CPU cores, graphics, orientation, device frame, boot (quick or cold; `emulator.start`'s `coldBoot` wins) and keyboard, each mapped to its `config.ini` key and format (step 1 (g)), with ranges bounded by the host; Go writes only those keys, each line outside them kept byte for byte, atomically (temporary file and rename), never through a symlink, never on a running or ambiguous AVD, never shrinking internal storage; creation is all or nothing; `emulator.configure` edits a stopped AVD (human-only, Q1; destructive, since a hardware change discards the quick-boot snapshot); `emulator.list` reports the values. Rejected: **a raw key and value map**: any key, and each key's format checked anyway; **launch flags (`-memory`, `-cores`) at each boot**: settings that persist belong to the AVD (emulator.md §Flags); **rewriting `config.ini` from a parsed map**: comments, order and unknown keys lost; **editing `hardware-qemu.ini`**: the emulator regenerates it at boot; **cameras, network, skins, a chosen snapshot and SD card resizing now**: outside the useful core, each a register row.
- **Q10. Three narrowings of ADR-0129 that step 1's evidence forces** (blocking for steps 3–6, not step 2; raised by the redraft's review, 2026-10-26). The documents say: ADR-0129 §8, "any doubt (an unreadable live process, …) counts as in use; zombies and vanished processes are skipped"; §7, running "by the emulator's lock"; §5, "an existing, non-empty directory that is not an SDK is refused". ADR-0130 supersedes none of these. Step 1 (f) found two setuid `login` processes in every terminal session whose `kern.procargs2` read fails with `EINVAL` (`P_svuid` 0); step 1 (d) did not observe the lock; and step 3's `sdk.acceptLicense` leaves a root holding only `licenses/` before the first install, which §5's test would then refuse. Draft decision, for the main session to record as a short ADR (`Supersedes: ADR-0129 §5, §7, §8 (in part)`, Delegated): (1) a process whose read fails and whose saved uid is not the user's is skipped, not a doubt, since an executable inside the user's SDK cannot be setuid to another user (Linux: the saved field of `Uid:`); (2) the emulator's lock counts only as a file held open in the `.avd` directory, through §7's open-file check; (3) a directory holding only `licenses/` and `.temp/` is an empty target. Alternatives: **counting setuid processes as doubts**: every update and uninstall refused on any Mac with a terminal open; **matching lock files by name**: a crashed emulator's stale lock blocks delete and edit until the user finds it, and the name was not observed; **creating the root's licence file elsewhere until the first install**: a second place AGP and Studio do not read. Steps 3 and 4 are written to (3), step 5 to (1), step 6 to (2). Recorded as ADR-0131, Accepted (Delegated, 2026-10-26).
