## Steps

### 1. Per-connection MCP sessions: the adapter's own loop over `HandleMessage`

- Builds: `adapters/mcp` `Serve` no longer calls `StdioServer.Listen`. Per connection, with that connection's own `MCPServer` as today: `sess := server.NewInProcessSession(<daemon session id>, nil)`; `srv.RegisterSession(ctx, sess)` (unregistered when the session ends); `ctx = srv.WithContext(ctx, sess)`. Any id unique per connection would do: `RegisterSession` refuses a duplicate only within one `MCPServer`, and each connection has its own; the daemon's `ses-…` id is used because it already names the session in the log. A read loop of our own over the hello's reader: each line that is a request runs `srv.HandleMessage(ctx, line)` in its own goroutine and writes the response; a notification is handled in the loop, in order; a response to a server request is dropped (Droidyard sends none). One writer serialises responses and the notifications drained from `sess.ClientNotifications()`; **before it writes a response, it writes every notification already queued on the channel**, so a notification a handler sent before returning precedes that handler's response on the wire (step 3 rests on it). At the end of input the loop sets `gone`, then cancels the request contexts, waits for in-flight handlers and unregisters the session: the 1b order, now in our code rather than inferred from `Listen`'s. `goneWriter` still drops every write once `gone` is set. `Serve`'s signature, the bound open before the first read (1c R4) and the per-connection `session` value stay. The worker pool goes (Readings R9).

### 2. The event bus, and `workspace.lifecycle`

- Builds: `internal/capability`: a `Publisher` interface (`Publish(topic, type, workspace, operation string, payload any)`), declared beside `Workspaces`, so `internal/capability` and `internal/workspace` publish without importing `internal/event`; `internal/event` imports `internal/capability`, never the reverse (B4: step 6's `events.*` descriptors live in `internal/event`). `internal/event`: `Bus`, which implements `Publisher`, with an `epoch` (`d-` + 8 random hex, D4) and a daemon-wide `seq` starting at 1; `Publish` stamps `epoch`, `seq` and `time` and appends to a ring bounded by 4096 events and 4 MiB of encoded envelope, whichever is reached first (D5); `Subscribe(topics, since)` returns a subscription with a bounded queue of 1024 envelopes (D5): with `since` in this epoch and still in the ring it first replays the matching events after `since.seq`; with `since` in this epoch but older than the ring it first delivers `events.gap {since.seq+1, oldest-1}`; with `since` of another epoch it first delivers `events.gap {1, oldest-1}`, which is `{1, 0}` while the ring still holds `seq` 1: an empty range that still tells the client the epoch changed and its state must be resynced, followed by the replay of everything the ring holds (D4); the ring snapshot and the registration happen under one lock, so nothing is missed or duplicated between replay and live. `Position()` returns the current `{epoch, seq}`. **Delivery is synchronous**: `Publish` assigns the `seq`, appends to the ring and enqueues the envelope into every matching subscription's queue, or records it as dropped there (the later gap), all under the one lock that `Position()` also reads, before it returns; so once `Publish` has returned, or once `Position()` has returned a `seq`, every matching event up to it is already in each subscription's queue or in its pending gap. A subscription offers a non-blocking `TryNext` beside its blocking read. A full queue never blocks `Publish`: the events that do not fit are dropped and one `events.gap {fromSeq, toSeq}` takes their place when room returns. `Close` ends a subscription and frees its queue. `internal/workspace`: the registry takes a `capability.Publisher` (nil in tests that do not care) and publishes every transition on `workspace.lifecycle` (D4): `type` the new state, `payload {state, degradedBy?}`, `workspace` the id. `cmd/droidyard` wires one bus into the registry.
- Implements: `capability-api.md` §Event envelope, §Subscriptions; `core-runtime.md` §Events; `workspace-state.md` §Observability; `core-runtime.md` §Package layout (`internal/event`); D4, D5.
- Check: in-process tests under `-race`. Order: 1000 events over three topics, global and workspace, have strictly increasing `seq`; two buses have different epochs. Filtering: a subscriber to `workspace.lifecycle` sees none of another topic's events. Resume: with eight publishers running, a subscriber that resumes from a `seq` still in the ring receives, replay then live, exactly the published events after it, each once (compared as sets of `seq`); `since` older than the ring delivers `events.gap {since.seq+1, oldest-1}` first; `since` of another epoch delivers `events.gap {1, 0}` first while the ring still holds `seq` 1, then every event in the ring, and `{1, oldest-1}` once it does not. Caps: the ring holds at most 4096 events and at most 4 MiB, each cap reached separately. Backpressure: with a queue of 16 (injected) and a subscriber that does not read, 10 000 publishes return within 1 s; the subscriber, once it reads, gets delivered events and gaps whose ranges together cover every `seq` of its topics, none silently. `Close` stops delivery. Synchronous delivery: 1000 times, with four other goroutines publishing on another topic, `Publish` on the subscription's topic is followed at once by `TryNext`, which returns that event (its `seq` equal to the one `Publish` assigned) every time; and an event whose `seq` is at most a `Position()` just read is always available to `TryNext`. ### 3. Progress on the bus, and MCP progress notifications

- Builds: `internal/capability`: the store takes a `capability.Publisher` (step 2; the bus at run time), never an `internal/event` type (B4); `Call.Progress` still sets `op.progress` and also publishes on `operation.progress` (D4): `type` `progress`, `payload {done, total?, message?, phase?}`, `operation` the operation id, `workspace` the operation's or `null`. `adapters/mcp` (imports `internal/event`, allowed by `core-runtime.md` §Adapter boundary): a tool call whose request carries `_meta.progressToken`, and `operation_wait` likewise, takes the bus position before `Start` (for `operation_wait`, before its wait) and subscribes from it to the topic `operation.progress`; the bus filters by topic only (D7), so **the adapter drops every event whose `operation` is not its own**. For each of its own events it sends `notifications/progress {progressToken, progress: done, total?, message?}` on its own session while it waits, from a forwarding goroutine that reads the subscription; an event whose `done` does not exceed the last sent is skipped, because MCP requires progress to increase (Readings R8). **When the wait ends**, whether the operation finished or the budget ran out, the handler stops the forwarding goroutine and waits for it to exit, takes the bus position `P`, then drains **without blocking**: it takes with `TryNext` what is already queued, sends its own events with `seq` ≤ `P`, and stops at the first empty read or the first `seq` above `P`; it then closes the subscription and only then returns the result. It never waits for a `seq` to reach `P`: `P` is daemon-wide, and the subscription carries only `operation.progress`, so the event at `P` may be on another topic and never arrive. The drain is complete because step 2's delivery is synchronous: the fixture's last `Progress` returned before its handler did, so before `Wait` returned, so its event is queued before `P` is read. Nothing is sent for the token after the result (the MCP specification: progress notifications stop when the request completes). The subscription's queue holds every operation's progress, so with many operations reporting at once it can overflow: the adapter skips the gap marker and sends what it still has, a progress notification being a nicety (`mcp-features.md` §7; Unverified). ## Design questions

None blocks the plan. The eight below are questions the documents do not settle; each is answered by the recommended option under the owner's delegation of 2026-10-03, labelled so the review can attack it. Where the answer belongs in an ADR or a design document, the orchestrating session writes it; the plan does not.

### D1. Per-connection MCP sessions — Delegated (owner, 2026-10-03)

- Affects: step 1 (and steps 3, 8)
- The documents say: ADR-0025 §Decision: "The session runs on the daemon's socket: `NewStdioServer(server).Listen(ctx, connReader, connWriter)`". `Listen` registers the package-level `stdioSessionInstance`, so notifications cross connections (1b plan §Not in this milestone; `docs/README.md` §Where the work stands). Nothing says what replaces it.
- Decision: the adapter runs its own read loop per connection and feeds `MCPServer.HandleMessage` with a context carrying a `server.NewInProcessSession(<id>, nil)` registered on that connection's `MCPServer` (any id unique per connection; the daemon's session id); one writer serialises responses and the session's notification channel, emptying the channel before each response; the adapter sets `gone` before it cancels request contexts. Public API only, the thin layer ADR-0025 §Consequences allows. Record as an `Amended:` line on ADR-0025 replacing the `Listen` bullet; the amendment also records that `mcp-go` drops a notification when the session's 100-slot channel is full (`sendNotificationCore`), which the adapter accepts for progress.
- Alternatives: a `ClientSession` type of our own (the same API and more code; kept as the fallback if `InProcessSession`'s marker or channel size proves wrong); forking or patching `mcp-go` (rejected: upgrades stay deliberate, ADR-0025); switching to the official SDK (ADR-0025 §Alternatives: heavier requirements; it wins only if `mcp-go` fails a criterion, and step 1's gate is where that would show).

### D2. The WebSocket library — Delegated (owner, 2026-10-03)

- Affects: step 7
- The documents say: nothing. The standard library has no WebSocket server; a new module requirement is a decision (planner rules; ADR-0025 is the precedent for MCP).
- Decision: `github.com/coder/websocket` v1.8.15, pinned in `go.mod`: no module requirements (its `go.mod`, read 2026-10-03), ISC licence, context-aware, application close codes, compression off by default. Its origin check is relaxed to the two allowed origins after our own fence ran (step 7). Record as a new ADR, shaped like ADR-0025.
- Alternatives: `github.com/gorilla/websocket` (requires `golang.org/x/net`); `golang.org/x/net/websocket` (its own documentation points to more complete packages; adds `x/net`); a hand-written RFC 6455 server (no dependency; framing, masking, fragmentation, ping and close handling become ours to get right and to test).

### D3. The default HTTP port, and "configurable" before a configuration file exists — Delegated (owner, 2026-10-03)

- Affects: steps 4, 5, 8
- The documents say: "The default bind is `127.0.0.1` on a configurable fixed port. If the port is taken, an ephemeral port is used instead" (`http-websocket.md` rule 1). No number, and no configuration format before Phase 1.
- Decision: the fixed port is the constant `7317`, outside both systems' ephemeral ranges (Linux 32768–60999, macOS 49152–65535); not configurable until the configuration file exists; tests set it through a seam. Not checked against the IANA registry (Unverified). Record in `http-websocket.md` rule 1.
- Alternatives: always ephemeral (the URL would change at every start, and a bookmark would never work); an environment variable (a new identifier that ADR-0024 would have to list, for a setting the configuration file will own).

### D4. Topics, event types and the gap marker — Delegated (owner, 2026-10-03)

- Affects: steps 2, 3, 6, 7
- The documents say: the envelope shape (`capability-api.md` §Event envelope), representative topic names, "`events.gap {fromSeq, toSeq}`", and "If it introduces a new topic, document the topic and its event types" (§Adding a capability). No document gives the types or payloads of `workspace.lifecycle`, names the topic progress goes to (`core-runtime.md` §Invocation: "Progress goes to the event bus, tagged with the operation id"), or shapes the gap marker as an envelope.
- Decision: `workspace.lifecycle`: `type` the new state (`opening`, `ready`, `degraded`, `closing`, `closed`), `payload {state, degradedBy?}`, `workspace` the id, `operation` absent. `operation.progress`: `type` `progress`, `payload {done, total?, message?, phase?}` (the fields of `Progress`), `operation` the id, `workspace` the operation's or `null`. The gap: an envelope with `topic` `events.gap`, `type` `gap`, `payload {fromSeq, toSeq}`, the current `epoch`, and `seq` equal to `toSeq` so a client that resumes from the last `seq` it saw skips what the gap covers. `seq` starts at 1 in every epoch. A resume from another epoch always begins with a gap `{1, oldest-1}`, which is the empty range `{1, 0}` (marker `seq` 0) while the ring still holds `seq` 1: nothing of the new epoch was lost, but the client still learns the epoch changed and must resync through queries, as `capability-api.md` §Event envelope requires; the ring's events follow. `epoch` is `d-` plus 8 random hex. The subscribable set is closed and published as an enum (step 6). Record in `capability-api.md` §Events and subscriptions as a topic table.
- Alternatives: progress on `operation.state` with `type` `progress` (mixes transitions and progress, which have different consumers); per-capability progress topics only, such as `build.progress` (MCP would need to know every domain's topic); accepting any topic string (a typo silently delivers nothing: "empty is a fact" would lie).

### D5. Bounds and the WebSocket event frame — Delegated (owner, 2026-10-03)

- Affects: steps 2, 7
- The documents say: the ring has "count and byte caps", the per-session send buffer "is bounded", and frames are `{"event": <event envelope>}`. No figures; nothing says which subscription a frame belongs to when a session has several.
- Decision: ring 4096 events and 4 MiB, whichever first; a queue of 1024 events per subscription, which is the bounded send buffer (a gap per subscription, not per connection); frames `{"subscriptionId": "<id>", "event": <event envelope>}`, an event matching two subscriptions sent once under each; a subscription's first frame, replayed `since` events included, is written only after a response envelope carrying its `subscriptionId` has been written on that session: the subscribe's own response, or, when that one carried none (its `waitMs` ran out with the operation `running`), the first later response on the same session that does (an `operation.wait` on it); until then its events wait in its queue. A response written on another session or over `POST /v1/call` does not release it: the subscription belongs to the session. A client never sees an id before the answer that gives it. Working defaults, to the configuration file later. Record in `capability-api.md` §Subscriptions, and in `http-websocket.md` §`GET /v1/ws`.
- Alternatives: one queue per connection (a busy subscription would cost a quiet one its events); deduplicating an event across a session's subscriptions (unsubscribing one would need to know what the other already delivered, and `since` resumes per subscription); frames free to precede the subscribe's response (the client would have to buffer frames for ids it does not know yet).

### D6. A session that can carry events — Delegated (owner, 2026-10-03)

- Affects: step 6 (and 7)
- The documents say: ADR-0010 and ADR-0019 §Sessions: a session is "one connection: one shim (one MCP session), one `droidyard call` invocation, or one WebSocket"; a stateful or streaming capability "invoked without a session" is rejected with `SESSION_REQUIRED`, "rather than silently degrading". But the native envelope has no event frame (`internal/daemon/native.go`), and `events.*` are not exposed over MCP (`mcp-tool-surface.md` §What is exposed). Read literally, a CLI call has a session and would be allowed to subscribe to events it can never receive.
- Decision: the core's session requirement means a session that can carry the capability's state and stream. In 1d only the WebSocket session sets one; a CLI call, an MCP session and plain HTTP get `SESSION_REQUIRED`, nextStep naming `GET /v1/ws`. The meaning of "session" is stated in four places, and all four change together; recorded by the orchestrating session as: (a) an `Amended:` line on ADR-0010 (§Decision: "reject … invoked without a session" means without a session that can carry that capability's state or stream); (b) an `Amended:` line on ADR-0019 §Sessions, whose "This is the session of ADR-0010" otherwise makes every `droidyard call` such a session; (c) the `SESSION_REQUIRED` row of `capability-api.md` §Error model reworded to "a stateful or streaming capability was called without a session that can carry it"; (d) a note on the CLI row of `capability-api.md` §Mapping to adapters that events "streamed to stderr or `--follow`" wait for a native event frame, not yet specified.
- Alternatives: accept `events.subscribe` from the CLI and drop the events (exactly the silent degradation ADR-0010 rejects); add an event frame to the native envelope now (a protocol change whose first real consumer, CLI `--follow`, is not in this milestone).

### D7. The `events.*` shapes — Delegated (owner, 2026-10-03)

- Affects: step 6
- The documents say: `events.subscribe({topics, filter, since})` "returns a `subscriptionId`"; consumers unsubscribe explicitly. Nothing gives `unsubscribe`'s behaviour on an unknown id, its annotations, or the filter keys.
- Decision: `subscribe` takes `topics` (at least one) and an optional `since {epoch, seq}`, and returns `{subscriptionId}`; `filter` is not in 1d (added later as an optional parameter, an additive change). `unsubscribe {subscriptionId}` returns `{}`, is idempotent, and is a no-op for an unknown id or another session's (no new error code, and no way to probe another session's ids); it is not destructive (override reason: "ends only the calling session's own subscription"). Recorded by the golden file; `capability-api.md` §Subscriptions gains one line.
- Alternatives: `filter` now with `workspace` and `operation` keys (no consumer in this milestone); `EVENTS_SUBSCRIPTION_NOT_FOUND` for an unknown id (a new code for a case `operation.cancel` already treats as a no-op when terminal).

### D8. The token file and the lock's `http` value — Delegated (owner, 2026-10-03)

- Affects: steps 4, 5
- The documents say: the token is "256 random bits … written to `<state>/run/http-token` (file `0600`, directory `0700`) and deleted on exit"; ADR-0021 §Format: "Every file carries `schemaVersion`"; `daemon.lock` already has none. ADR-0019 §5: "Before binding anything the daemon takes an exclusive `flock` on `<state>/daemon.lock` and writes `{pid, startTime, version, socket, http}` into it": the HTTP address is not known until the listener is bound.
- Decision: the file holds the token as 64 lowercase hex digits and a newline, no JSON and no `schemaVersion`, as `daemon.lock` is not versioned either: both are per-launch runtime files that no later version reads. A stale file from a crashed daemon is removed and recreated `0600` at start. The lock's `http` is `"127.0.0.1:<port>"`, written by a second, in-place rewrite of the lock after the HTTP bind and before the socket bind, new contents first and truncation after (step 5). Record as an `Amended:` line on ADR-0021 (§Format applies to state files; `daemon.lock` and `run/` are runtime files) and an `Amended:` line on ADR-0019 §5 (the lock is written before binding anything, with `http` `null`, and rewritten in place once the HTTP listener is bound, before the socket).
- Alternatives: a JSON file `{schemaVersion, token}` (every reader parses JSON for one string, and the browser URL needs the bare token anyway); base64url (43 characters; hex is unambiguous in a URL fragment and in a terminal).

## Readings the steps take

Not questions: each follows from a cited document and is cheap to change.

- **R1. API version `0.3.0`.** Settled by the documents, not delegated (D9 in the first draft): new capabilities and codes go in a minor version (`capability-api.md` §Error model, "new codes may be added in a minor version"; §Discovery and versioning, "`since` records the API version that introduced a capability"), and ADR-0019 §7 detects a stale daemon only by a differing version, the reason 1c bumped to `0.2.0` (1c plan R2). So `0.2.0` → `0.3.0` in step 6, with the first schema change; `events.*` carry `since` `0.3.0`; the existing entries keep their pinned `since`. A `0.2.0` daemon still running is then refused by a `0.3.0` shim with `DAEMON_VERSION_MISMATCH`, instead of accepting a `ui` call it has no HTTP listener for.
- **R2. Fence order.** Host, Origin, preflight, token, content type, size, then JSON: the cheapest rejection first, and every one before routing (`http-websocket.md`: "The adapter enforces every rule **before** it resolves a capability").
- **R3. Bind before the socket.** The HTTP listener is bound, the token written and the lock's `http` set after reconciliation and before the socket is bound, so anything that reaches the socket finds them (ADR-0019 §5 writes `http` "into" the lock; this makes it true by the time any client looks). A failure to bind either the fixed or an ephemeral loopback port stops the start, as a non-loopback address does.
- **R4. Opening the browser.** `open <url>` on macOS, `xdg-open <url>` on Linux, the standard launchers; ADR-0019 §3 says only "opens the browser". `ui` takes `--no-autostart` like every auto-starting subcommand (ADR-0019 §4).
- **R5. The loopback guard.** With no configuration file the address is the constant `127.0.0.1`; the guard that refuses a non-loopback address (rule 1) is written now, tested as a unit, so the Phase 1 configuration cannot bypass it. It accepts `[::1]`, which is loopback, but rule 2's `Host` allowlist names only `127.0.0.1:<port>` and `localhost:<port>`: a listener bound to `[::1]` would refuse every request whose `Host` is `[::1]:<port>`. Unreachable in 1d, where the address is always `127.0.0.1`; flagged for the Phase 1 configuration, which must either add `[::1]:<port>` to the allowlist or refuse `[::1]`.
- **R6. The placeholder page.** `GET /` serves one static, embedded HTML page saying the web UI arrives in Phase 2, with no script and no data, under rules 1 to 3 and 7 and without the token (`http-websocket.md`: "The static UI bundle is served without the token, because it contains no data"). `GET /assets/*` is `404` until there are assets.
- **R7. `400` versus an envelope.** `http-websocket.md` lists `400` for "malformed JSON" and `200` with an envelope for every rejection: a body that is not JSON is `400`; JSON that is not a valid envelope is `200` with `REQUEST_INVALID_PARAMS`, as the native adapter answers it.
- **R8. Increasing progress.** MCP requires each `notifications/progress` to increase; a `done` not above the last sent is skipped rather than sent out of contract.
- **R9. No worker pool.** Each MCP request runs in its own goroutine, as `mcp-go`'s own non-tool requests do (`server/stdio.go` `requestWg.Go`); the pool of 100 existed only because `Listen` queued tool calls, and a call queued behind it could not be cancelled (1b plan, step 5's Not here).
- **R10. Shutdown order.** The HTTP listener closes with the socket listener ("stop accepting"); WebSocket sessions close with the other sessions; the token file is deleted before the lock is released (`process-lifecycle.md` §Shutdown, extended to the new listener).
