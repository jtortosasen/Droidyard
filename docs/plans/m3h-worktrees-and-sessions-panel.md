## Design questions

Delegated (the main session, under the owner's standing instruction to apply the recommended option, 2026-10-27). The main session writes ADR-0134 from these at step 1; none blocks the plan.

- **Q1. The top part and the project switch.** The documents say: ADR-0047 §1 (a panel of every project), ADR-0083 §2 (each project with its sessions and worktrees), ADR-0127 §4 (Projects keeps project and worktree rows), and ADR-0127 §Alternatives considered rejected "the whole column as Client → Project → chat" because a project with no chat could not be opened and worktree rows, Release and Remove would lose their place. Recommended: the top part is the tab's project only, its main tree (`primary`) and linked worktrees from `workspace.describe` merged with `workspace.watch`'s rows, with nested live sessions, holds and Release (step 3, 4); every project stays one click away in the in-panel menu on the project's name, with Remove, Open folder… and the typed root, open by itself with none selected; so what ADR-0127's rejection protected keeps its place. `describe` is read on the chats' cadence (a burst one read after 1 s, 30 s, on reconnect): it is the one contract that lists worktrees not opened (ADR-0089 §3). ADR-0089 §Alternatives considered rejected `worktrees` on `workspace.watch` for "more reads on every open and every panel refresh, for a field only the agent's choice needs"; the panel now needs it too, and polling `describe` for the tab's project only (one bounded Gradle resolution and worktree listing a read, an operation record like `session.chats`') keeps the streams and every other project's opens unread, which widening `watch` would not. Rejected: **`git.refs`'s worktrees** (the Git panel's): it runs git and lists entries git would prune (ADR-0089 §Consequences), and lives in the project view, not the column; **only the opened worktrees** (today's): a worktree an agent made and has not entered is invisible, the owner's "current worktrees"; **every project's trees in the column**: the redundancy the owner named; **a popover menu**: the overlay hides on a pointer outside it (ADR-0052 §3).
- **Q2. Sessions, connections and "uses Droidyard".** The documents say: ADR-0127 §4 (Client → Project → chat; an unclaimed session a row under its client), ADR-0095 §1 (Cursor unjoined), ADR-0088 §2, §4, §Alternatives considered (chat ids in memory only, 256, never published by `session.watch`, persisting them rejected). Finding: the daemon keeps no record of which chats used it beyond the live join; past use would need a new published field from a memory lost at each restart, so a chat would flip after one, and persisting it is the rejected alternative. Recommended: "Droidyard" means **connected now**; no contract change. Folders by project, the tab's first; each row's client a tag from its store; no client header; a live session no chat claims is no row (nested on its tree, or a connected tag on its folder's head), a peer's link only in Devices (ADR-0104 §1); presence `connected` / `not-connected` / `unknown` as step 3 defines, so the panel never claims "not connected" for a chat that may be the live one (Cursor's case) and never guesses which it is. Tag wording "not connected" (the owner may reword at step 6). **A client's tag carries its own hue** (the owner asked for colours and tags that carry information): this supersedes ADR-0128 §1's "colour means state, nothing else" in part, for client tags only, with the condition that the hue always sits beside the client's name, so colour is never the only carrier, and every hue passes §3's floor. Rejected: **past use from the in-memory chat map**: daemon-life only, Claude Code only, and a contract change for a mark that resets; **a persisted record of chat ids**: ADR-0088 §Alternatives considered; **dimming every Cursor chat**: it marks the live one "not connected"; **matching a Cursor connection to its newest chat**: a guess the owner's brief excludes; **keeping a row for an unclaimed connection**: the rows the owner did not understand; **neutral tags** (name and icon, no hue, ADR-0128 §1 as written): the owner's "colours that carry information" and Orca's per-client mark, where the name already carries the meaning.
- **Q3. The kept selection.** The documents say: ADR-0083 §3 (a selection made from a session's row follows it; from a project or worktree row stays). Recommended: the followed session is marked with the selection edge wherever it is shown; its move selects its worktree (as today) and the top part marks it, listed through `workspace.watch` even before `describe` reads again; any navigation to another workspace ends the follow (`routed`), closing row 518 clause 1. `selectedKey`, Activity's filter, is unchanged. Rejected: **marking by `selectedKey`**: it outlives the follow (a tree click leaves Activity filtered) and would mark a session the selection no longer follows; **ending the follow only on panel clicks** (today): the address bar keeps pulling the tab.
- **Q4. Title and status bar.** The documents say: nothing. Recommended for the shape (Delegated): the project's name is the listed main tree's name, else the base name of `mainRoot`; the status bar shows the tree's name with a branch icon, or the project's with `primary` on the main tree. Rejected: **the worktree's name in the title** (the first draft): the owner's correction; **the tree in the title too** (`Droidyard - proj / wt-a`): the owner asked for the project only, and the status bar now says where.
