## Emulator rules

Runs on real emulators are the main session's only (the implementer never runs `adb`, `emulator`, `avdmanager` or a daemon against a device, m1g S4).

- E1. The shared adb server on 5037 is never killed, restarted or reconnected (m1f E1); its pid (`lsof -nP -iTCP:5037 -sTCP:LISTEN`) is recorded before and after each run and must match.
- E2. Daemon builds used in runs carry `-tags droidyard_nodump`, checked with `go version -m` (m1f E3; uniform with 1f–1h).
- E3. **`Pixel_9a` (`emulator-5554`) is never stopped, wiped, rebooted, killed, installed on, launched on, or read through the UI reader.** No call names it: no row of this plan starts, adopts or stops it, and `emulator.list` and `device.list` merely list it. Its `qemu-system-aarch64` pid is recorded before and after each run and must match.
- E4. **The other five AVDs** (`Medium_Phone_A17`, `Pixel_10_Pro_XL`, `Pixel_4a`, `Pixel_6a_A17`, `Pixel_Tablet`) are never named in a call, started, stopped or wiped. Every daemon of this milestone runs with `ANDROID_AVD_HOME=~/Library/Caches/droidyard-dev/m1i/avd` (one exception: step 4's listing daemon, which receives `emulator.list` alone, then `droidyard stop`), so its launcher lists the scratch AVD alone and no call can start or wipe another AVD by name (step 1 G8 confirms this before any daemon relies on it). `stat -f %m` of each of their `userdata-qemu.img*` files is recorded at the start and end of each run and must match.
- E7. **The adb guard.** An AVD home does not protect a running emulator from calls that name its serial (`emulator.stop`, every `device.*` call). So every daemon of this milestone runs with `ADB=~/Library/Caches/droidyard-dev/m1i/bin/adb`, a script the main session writes at step 1 that `exec`s (replaces itself with, so pids, the pid kill of m1e R8 and a follow's pid record see `adb` itself) the host SDK's `platform-tools/adb`: the same binary, so the client and server versions match and E1 holds. It fails closed: it passes `version`, `devices` and `devices -l` with no serial; any command whose first arguments are `-s <serial>` for a serial not in `m1i/bin/protected`; and, for a protected serial, exactly `shell getprop`, `shell getprop sys.boot_completed` and `emu avd name` (what `device.list`, the preamble and `emulator.list` run), compared as whole argument lists, so `shell getprop x; <cmd>` does not pass. Everything else (`-t`, `-e`, `-d`, a command relying on `ANDROID_SERIAL`, any other command) prints `m1i adb guard: refused` on stderr, appends the arguments to `m1i/bin/refused.log` and exits 97, running nothing. `protected` is written, and `refused.log` truncated, at the start of each run: `protected` from `adb devices`, every serial online before the scratch emulator boots (`emulator-5554` at least). Step 1 checks the guard in its dry-run mode (`M1I_GUARD_DRYRUN=1` prints what it would `exec` instead of running it): `emu kill`, `install`, `shell monkey`, `forward`, `logcat`, `shell input` and `shell getprop x; reboot` on `emulator-5554` and `-t 1 emu kill` refused; `emu avd name`, `shell getprop`, `devices -l` passed. Never checked with a real stop. If an emulator other than `Pixel_9a` and the scratch one is online at a run's start, the run does not start.
- E5. **The scratch AVD `droidyard_m1i`** is the only AVD booted, stopped or wiped, by hand (step 1) or by a daemon. Step 1 creates it with the SDK's `avdmanager` (ADR-0005: the SDK's own tool, not the `android` CLI) from `system-images;android-31;google_apis;arm64-v8a` (installed; no Play Store, no account), under the isolated `ANDROID_AVD_HOME`; `ls ~/.android/avd` is unchanged by its creation. It is deleted at step 6's end. Its emulator is stopped at the end of every run that booted it. Only the fixture's APKs are installed on it.
- E6. On any device, Droidyard touches only its own files, processes and forwards (m1f E6).

Why a scratch AVD (D2): `emulator.stop` and `emulator.wipe` destroy an AVD's running state and user data, and only an AVD created for the run is provably nobody's. Two structural fences back the rules, so a mistaken call (the agent's in step 6 included) fails instead of being caught afterwards: the isolated AVD home makes starting or wiping an owner AVD by name impossible (the launcher does not list it), and the adb guard (E7) refuses every serial-named write to an emulator that was online before the scratch one. API 31 also gives spike S9 a second API level beside `Pixel_9a`'s 36.1. Adoption is proven on the scratch AVD booted by hand, never on an owner AVD.

## Readings

- R1. **API `0.8.0`**, bumped by step 2, the first schema change (additive, `capability-api.md` §Discovery and versioning).
- R2. **Classification** (`capability-api.md` §Classification of the MVP surface; `mcp-tool-surface.md` §The MVP tool surface): `device.logs` G/Q/LR, read-only, idempotent, open world, untrusted, `[adb]`; `emulator.list` G/Q, `[emulator, adb]`; `emulator.start` G/C/LR, idempotent, not destructive (the documented override: "adopts a running AVD and joins a boot already in flight"), `[emulator, adb]`; `emulator.stop` G/C, destructive, not idempotent, `[adb]` (it needs no launcher, `emulator.md` §Stop); `emulator.wipe` G/C/LR, destructive, not idempotent, `[emulator, adb]`. Open world follows from the availability requirements. 32 capabilities and 30 MCP tools after step 5.
- R3. **Untrusted fields**: `device.logs`' line `tag` and `message`, `crashes[].exception` and `.message`, and the capture artifact (ADR-0015 §1: logs are device text). `emulator.*` carries none: AVD names and configuration are host files, and `emu avd name` is the emulator's console, a host process.
- R4. **Caller input never reaches a path or a shell unchecked.** `applicationId`: `launch.go`'s pattern. `tags`, `contains`: filtered host-side only, never in adb arguments. `since`: parsed, then re-formatted by us. `buffers`, `minPriority`: enums. `avd`: `^[A-Za-z0-9][A-Za-z0-9._-]{0,99}$` and then present in the launcher's `-list-avds` output, both before adoption, any file path or any spawn (no `..`, no leading dot, no separator; the order is D15's). `device`: an `adb -s` argument, as today. `adb … logcat` and `adb … shell …` join their arguments into a device shell command: everything in them is a constant, an enum value, a pattern-checked id or a number we formatted.
- R5. **Locks** (`core-runtime.md` §Concurrency): `device.logs` holds no key (reads run in parallel); `emulator.start` and `wipe` hold `emulator.boot`, `emulator.stop` holds `device.write:<serial>` (D12); `device.launch` keeps `device.write:<serial>`.
- R6. **Dependencies and state.** No new Go module. No new file kind under the state root: `<state>/emulator/<avd>.log` is ADR-0021 §Layout's, and a follow's pid record goes in `processes.json` (ADR-0021 §Pid records: the durable exception, which names "a logcat … stream"). New error codes: `emulator.md` §Failure modes' seven (`EMULATOR_LAUNCHER_NOT_FOUND`, `_AVD_NOT_FOUND`, `_LAUNCH_FAILED`, `_AVD_LOCKED`, `_BOOT_TIMEOUT`, `_NOT_AN_EMULATOR`, `_STOP_TIMEOUT`) and D10's `DEVICE_LOGS_FAILED`. Environment read: `emulator.md` §AVD discovery's variables, from the daemon's environment passed in, never `os.Getenv` in domain code (as `sdk.Host(env)`).
- R7. **No `android` CLI**, for the product or for runs: ADR-0005 §Decision ("Do not depend on Android CLI … emulator/SDK tools (`emulator`, `avdmanager`, `sdkmanager`)"). The `android emulator start` it offers also returns only once booted, owning the wait the boot sequence must own.

## Delegated decisions

Taken under the owner's standing instruction; each can be reverted.

- D1. **Scope: `device.logs` and `emulator.*`**, the two golden-path gaps (steps 4 and 6); `file.*` and `policy.*`/`shell.exec` deferred per §Scope. Nothing here needs either.
- D2. **The scratch AVD** of §Emulator rules E5, for every boot, adoption, stop and wipe; no call names `Pixel_9a` (E3), fenced by the AVD home (E4) and the adb guard (E7).
- D3. **Fixture crash path.** `sidecar/testdata/flavoured`'s `MainActivity` gains `Log.i("DroidyardFixture", "created " + getPackageName())` in `onCreate` and a `Button` labelled `Crash` (`setAllCaps(false)`, so the tree reads `Crash` on every API level) whose click throws `IllegalStateException("droidyard fixture crash")` (plain `android.widget`, no AndroidX); the package-name text stays (1h's level-5 row reads it). Debug builds are debuggable, so `run-as` reaches the process for step 1's native crash.
- D4. **`device.logs {device, applicationId?, since?, tags?, minPriority?, buffers?, contains?, maxLines?, followMs?}`** → `{device, window {from, to}, filter {applicationId?, by: uid | pids | none, uid?, pids[]}, lines [{time, pid, tid, priority, tag, message, crash?}], crashes [{pid, time, exception, message}], counts {scanned, matched, returned}, truncated, emptyReason?: noLines | noKnownProcess | filtered, capture?: ArtifactRef, warnings[]}`. Times are device-clock RFC 3339 UTC with microseconds when the format gives them. `priority` is `verbose|debug|info|warn|error|fatal`; `minPriority` the same enum. `buffers` ⊆ `main|system|crash`, default all three (logcat's default set); with an app filter `crash` is always read (§Filtering 3). `tags` ≤ 20 exact tags, `contains` one literal substring ≤ 256 bytes matched against the message. `maxLines` 1–1000, default 100: the newest matching lines inline; `truncated: true` with a hint (narrow the filter, read `capture`) when more matched. The doc's `follow?` is spelled `followMs` (D9).
- D5. **App filter by uid, host-side.** The uid comes from `pm list packages -U <applicationId>` (exact `package:` match), read on each call (a reinstall can change it). Lines are read through the format step 1 picks, with the uid column, and kept when their uid is the app's; crash-buffer lines are kept by block (D6). One read of the stream then serves the app's lines and the native crash blocks tombstoned writes under its own uid, so a follow needs one child, not two. Support of the column is probed once per device per daemon and cached (`adb-device.md` §Filtering by app survives the app's death, item 1), keyed by serial and `transport_id` from `devices -l`, since an emulator serial is reused by other AVDs and images. Where the column is missing or unusable, `by: pids` (D11). **If step 1 finds the column unusable where `logcat --uid` works**, the device-side flag plus a separate crash-buffer read replace it, recorded under Changes before step 2. **A departure in mechanism, not in decision: the owner should see it.**
- D6. **Crash blocks.** Lines are grouped into blocks by `(buffer, pid, tag)` contiguity; a block is the app's when it names exactly its `applicationId` (whole-token match, not a prefix): Java `Process: <applicationId>, PID: <pid>` under `FATAL EXCEPTION`, native `>>> <applicationId> <<<` (exact text per step 1). Under `by: uid` a Java block must also carry the app's uid (the crashing process writes it itself), so another app cannot claim a crash by logging a forged header; a native block is written by tombstoned and is matched by its header alone. Its lines carry `crash: true`; its pid joins the pid history. `crashes[]` (at most 20, newest kept) takes `exception` and `message` from the Java exception line or the native `signal N (SIGX)` line. Without an app filter, every crash block is summarised.
- D7. **Bounds.** The capture is filtered while read, then bounded: inline per D4; the capture artifact holds the matching lines in logcat's own text, newest kept, at most 4 MiB (`truncated` and a dropped count when cut), so the ephemeral store's deferred spill (ADR-0012 `Amended:` 2026-10-04: "until a producer routinely exceeds 4 MiB") is never reached; one logcat line at most 16 KiB, cut at a UTF-8 boundary. No scan cap: `logcat -d` prints oldest first, so stopping early would drop the newest lines (the crash); the read is bounded by the device's buffer size (step 1 G7) and its timeout. The snapshot's `logcat -d` gets 20 s (past it, what was read is returned with `truncated` and a warning saying the newest lines are missing, since `-d` prints oldest first), `pm` 5 s. No `capture` when nothing matched.
- D8. **`since`**: `"launch"` or an RFC 3339 timestamp read as device-clock time (as `launchedAt` is), passed to logcat's `-T` in the form step 1 confirms. Default for a snapshot: `"launch"` when `applicationId` is given and a launch of it on that device is recorded; otherwise the whole buffer, of which the newest `maxLines` are returned (the "tail"). A follow has no default `since` (D9). An explicit `"launch"` with no recorded launch is `REQUEST_INVALID_PARAMS`, nextStep "call device.launch, or pass a device-clock timestamp".
- D9. **Follow**: `followMs` 1000–60000, "what happens next": without `since` the window starts at the device clock read first (`date +%s.%N`, as `launch` reads it), whatever launch is recorded; an explicit `since` (a timestamp or `"launch"`) adds the backlog from it first. One child `adb -s <serial> logcat <format> -b <buffers> -T <from>` (no `-d`), read line by line and filtered as it arrives, ended at the window by killing the client's pid, as `Run` does (m1e R8). The child gets a pid record for its life (ADR-0021 §Pid records: the durable exception), through a new `process.Supervisor.SpawnRecorded`, so a daemon killed mid-window leaves nothing the next daemon does not reap; reconciliation kills the recorded process group, which spares a forked adb server only because real adb puts its server in a group of its own (observed once, m1e step 1: pgid 59756 against the client's 59755, on port 5199). The record needs the pid, so it is written once the child started; if it cannot be written, the child is killed by its pid (R8) before any line is read and the call fails `DEVICE_LOGS_FAILED` naming the state store, no client left. The record's `kind` is a new value, `device-stream`, beside `shared-sidecar` and `workspace-sidecar`; `Reconcile` treats every kind alike. Cancel and a graceful daemon stop end the call `cancelled` with no partial result (ADR-0020); a device that disconnects mid-window is `DEVICE_DISCONNECTED` (the runner's existing mapping). `adb-device.md` §Logs says the follow child is "killed as a process group": in the run it is killed by pid (m1e R8, which keeps the shared server safe even if it ever shares the group), at reconciliation by group. **The owner should see it.**
- D10. **`DEVICE_LOGS_FAILED`**: logcat or `pm` exits non-zero, or its output is not the requested format, on a ready device; or a follow's pid record cannot be written (D9). `cause` names the command and exit status or the format mismatch, never a device line (`capability-api.md` §Untrusted outputs). Documented in `adb-device.md` §Failure modes by step 2 (the m1e `DEVICE_SCREENSHOT_FAILED` and m1g D9 pattern).
- D11. **The app record**: per `(serial, applicationId)`, in memory, the latest `launchedAt` and a pid history (at most 16 pids with first and last seen; at most 256 records, least recently used dropped), fed by `device.launch`, by `pidof` at each `device.logs` call, by `Start proc <pid>:<applicationId>/` lines and by crash blocks (`adb-device.md` §Filtering by app survives the app's death, item 2). `by: pids` filters by every pid whose span overlaps the window. `emptyReason`: `filtered` when the app had lines that tag, priority or substring excluded; `noLines` when a process of the app is known in the window (a pid, a launch, a line before filtering) and none of its lines matched; `noKnownProcess` otherwise.
- D12. **Two keys** (a descriptor holds one scheduler key per call, `internal/capability/descriptor.go`). `emulator.start` and `wipe` hold `emulator.boot`, the boot slot `emulator.md` §Concurrency serialises ("boots are serialised"); a per-AVD key would not serialise boots, and a second key per call does not exist. So a second `start` of a booting AVD is `queued` with `blockedBy`, then adopts, as documented. `emulator.stop` holds `device.write:<serial>`: a `device` cannot be mapped to its AVD at `Start` (no I/O, ADR-0020), and this key serialises it with installs and launches on that device and lets it end a stuck boot, the remedy `emulator.md` §Failure modes and §Timeouts imply, instead of failing `OPERATION_QUEUE_TIMEOUT` behind it for as long as the boot waits. Consequences: `emulator.md` §Concurrency's example ("`emulator.stop` behind a boot in progress" times out) no longer holds. A stop of an emulator whose boot is in progress kills it, and that boot ends at once: the boot loop reads the launch table on every poll, and once our launcher has exited (it does after `emu kill`, step 1 G12) it fails `EMULATOR_LAUNCH_FAILED` with the cause "the emulator exited during boot", the exit status and the log tail, never polling on to the boot timeout (which would hold the boot slot for up to 180 s); `emulator.md` §Failure modes' `EMULATOR_LAUNCH_FAILED` row widens from "before a device appears" to "before the device finished booting". A `start` of an AVD that is already running queues behind an unrelated boot before adopting it. An adoption whose serial leaves while it waits for readiness (a concurrent `stop`) fails `DEVICE_DISCONNECTED` naming the serial, nextStep "call emulator.start again"; a boot started while a stopped AVD still holds its lock may fail `EMULATOR_AVD_LOCKED`. A wipe's own stop holds only the boot slot. No ADR fixes per-AVD locking (ADR-0020 §States names "an AVD" as an example of a lock); `core-runtime.md` §Concurrency ("`emulator.start/stop/wipe` per AVD") and `emulator.md` §Concurrency and §Failure modes are reconciled at the close. **The owner should see it.**
- D13. **`emulator.list`** → `{avds [{name, running? {device}, config? {target, abi, deviceProfile, displayName}, configUnavailable?}], warnings[]}`: names from `emulator -list-avds` (chatter filtered per step 1's recording), configuration from `emulator.md` §AVD discovery's directories in its order, `config.ini` read bounded (64 KiB); a listed name without a readable entry keeps `configUnavailable` with the reason, never dropped; `running` from the online emulator serials and `emu avd name`. No paths in the result.
- D14. **Timeouts are constants**: boot 180 s (`emulator.md` §Timeouts calls it configurable; no configuration key exists, `capability-api.md` §Open questions), stop 20 s, `-list-avds` 10 s, readiness polled every second. **The owner should see it.**
- D15. **The launch.** The launcher resolved per `emulator.md` §Binary resolution (`sdk.Host(env)`'s root, then from adb's location, then `PATH`), started directly with `exec.Cmd` and `SysProcAttr{Setsid: true}`, never through the supervisor (no pid record, no `Pdeathsig`: `emulator.md` §Detached launch; `process-lifecycle.md` §Shutdown, layer 2), stdin `/dev/null`, stdout and stderr to `<state>/emulator/<avd>.log` truncated at each boot, cwd the state root, the daemon's environment. One goroutine per launch calls `Wait`; an in-memory table `avd → {pid, exited}` serves `EMULATOR_LAUNCH_FAILED` (exit before the device finished booting, read on every readiness poll: status and the log's last 20 lines, at most 2 KiB) and `stop`'s wait. Adoption waits for `sys.boot_completed` like a boot, within the same 180 s (`emulator.md` §Capabilities: "once online and booted"). Order: the name's pattern, then its presence in `-list-avds`, then adoption, then the log path and the spawn. The presence check before adoption makes adoption depend on the launcher listing the name, which `emulator.md` §Boot sequence 1 avoids; it is kept on purpose: it fences every AVD the launcher does not list (E3, E4) and gives `EMULATOR_AVD_NOT_FOUND` its candidates.
