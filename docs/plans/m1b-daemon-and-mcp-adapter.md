## Steps

### 1. Operations in process, and the two operation capabilities

- Builds: `internal/capability`: `Start`, `Wait`, `Cancel`, `Invoke`; an operation store keyed by daemon-wide ids; strict parameter decoding (unknown fields rejected); the scope check (`REQUEST_MISSING_WORKSPACE`, `REQUEST_UNEXPECTED_WORKSPACE`); the audience check by the caller's client kind (`REQUEST_NOT_ALLOWED_HERE`); retention of terminal operations for 15 minutes and at least the last 200. `operation.wait {operationId, timeoutMs?}` and `operation.cancel {operationId}` registered by the core, whose calls bypass the store. `OperationView` moves to `internal/capability`, where both `schema` and the adapters can use it; its `result` becomes a named open-object type whose reflected schema is `{"type":"object"}` (a `JSONSchema()` method, the hook `invopop/jsonschema` honours), because a bare `json.RawMessage` reflects as the empty schema `{}` (`invopop/jsonschema` v0.14.0 `reflect.go`), which is not ADR-0020's "open object". `Call` gains `OperationID`, set by `Start` before the handler runs: ADR-0020 makes a build's id its operation id (§Operation capabilities, "the build id *is* the operation id"), so a handler needs it, and a fixture handler uses it to hand its id to the test (steps 5, 7). The request and response envelope types live there too (Readings). Both registries that must agree (`registry()` in `cmd/droidyard/main.go` and in `internal/schema/schema_test.go`) register the two capabilities.
- Implements: ADR-0020 §Core primitives, §Operation capabilities, §States (without `queued`), §Retention; ADR-0015 §6 (the core rejects human-audience calls from an MCP session); `docs/architecture/capability-api.md` §Operations and cancellation.
- Check: new tests in `internal/capability`, one decision each: `Start` returns a typed error and creates no operation for an unknown capability, an unknown parameter field and a superfluous workspace; `Wait` with a past deadline returns `running` and changes nothing; `Cancel` ends an operation `cancelled` with `OPERATION_CANCELLED` and no result; a handler error ends it `failed`; a terminal operation is waitable until retention expires, then `OPERATION_NOT_FOUND` (fake clock); N calls to `operation.wait` leave the store size unchanged; a handler's `call.OperationID` equals the id `Start` returned; a human-audience fixture is rejected with `REQUEST_NOT_ALLOWED_HERE` for client kind `mcp` and accepted for `cli` (this is the core half of A5's human-audience clause; over MCP the library refuses first, step 4). Run with `-race`. Then `go test ./internal/schema` fails with the diff below, and `-update` is run only if the diff is exactly that.
- Schema: two entries added, nothing else changes, `version` stays `0.1.0` (see Readings). `operation.cancel`: `kind` command, `scope` global, `statefulness` stateless, `audience` all, annotations `readOnlyHint` false, `destructiveHint` true, `idempotentHint` true, `openWorldHint` false, errors include `OPERATION_NOT_FOUND`, input `{operationId}` required, output an empty object. `operation.wait`: `kind` query, annotations read-only, not destructive, idempotent, not open-world, errors include `OPERATION_NOT_FOUND`, input `{operationId}` required plus optional integer `timeoutMs`, output the operation view `{operationId, capability, state, progress?, blockedBy?, result?}` with `result` exactly `{"type":"object"}` (emitted deliberately, see Builds; not `{}`) and no `error` field: the golden `output` is the MCP projection, as it is for long-running capabilities (Readings, `operation.wait`). Both annotation sets match the `operation_wait` and `operation_cancel` rows of `docs/interfaces/mcp-tool-surface.md` §The MVP tool surface.
- Needs: nothing earlier; fixture handlers only.
- Not here: `queued`, `blockedBy`, the 20 s queue bound (no per-resource lock exists yet; `docs/architecture/core-runtime.md` §Concurrency puts the first at devices); idempotency keys (no descriptor sets `AcceptsIdempotencyKey`); `WORKSPACE_NOT_OPEN` (no workspace registry until 1c); progress events (no event bus until 1d); the native envelope of `operation.wait` (step 3, where the envelope exists).
- Rests on: an operation's lifetime belongs to the store, not to any caller's context: abandoning a `Wait` does not touch the operation (ADR-0020 §Core primitives, "Waiting has no side effects"). Needs level 4 here; steps 5 and 7 take it to level 5.
- [x] Done. Each seen failing once with its decision reversed (8 mutations, source restored). `-race -count=30`: ok. `go test ./internal/schema` failed first; `go test ./internal/schema -update` then `git diff --stat schema/capabilities.json`: "119 insertions(+)", no deletions: `operation.cancel` and `operation.wait` added as the Schema line states (`result` `{"type":"object"}`, `required: ["operationId"]`), `version` `0.1.0`. `go build ./...`, `go vet ./...`, `gofmt -l .`: no output; `go test -count=1 ./...`: ok for all four packages with tests.

### 2. State root, socket path and the single-instance lock

- Builds: `internal/platform`: the state root (`DROIDYARD_STATE_DIR`, else `$XDG_STATE_HOME/droidyard` defaulting to `~/.local/state/droidyard` on Linux, `~/Library/Application Support/droidyard` on macOS) and the socket path (`<state>/run/droidyard.sock` when `DROIDYARD_STATE_DIR` is set or on macOS; `$XDG_RUNTIME_DIR/droidyard/droidyard.sock` on Linux, else `<state>/run/`; `/tmp/droidyard-<uid>/<root-discriminator>/` when the path exceeds `sun_path`, the discriminator a short hash of the canonical state root, per ADR-0019 §6 as amended 2026-09-30). `internal/daemon`: `flock(LOCK_EX|LOCK_NB)` on `<state>/daemon.lock`, then its contents written in place (not by rename, which would detach the locked inode). `droidyard serve` takes the lock and holds it until `SIGTERM` or `SIGINT`.
- Implements: ADR-0019 §5, §6; ADR-0021 §Location, §Layout, §Locking; ADR-0024 §Decision (names).
- Check: a table test of the path rules over environment combinations, one row asserting that an explicit `DROIDYARD_STATE_DIR` beats `$XDG_RUNTIME_DIR` and one asserting the `sun_path` fallback; `TestSecondServeLosesTheLock`: two `serve` processes (the test binary re-executed as `droidyard`) on one temporary state, the second exits non-zero and `daemon.lock` names the first pid. Real processes, real `flock`.
- Schema: no change.
- Needs: nothing earlier; the stdlib's `syscall.Flock`.
- Not here: the socket (step 3); `http` in the lock is `null` until 1d; kernel process start times (pid records, 1c). The lock's `startTime` is the daemon's own clock at start (see Readings).
- Rests on: `flock` excludes a second process on the same file on macOS, and the kernel releases it when the holder dies. Level 5, reached by the re-executed processes.

### 5. MCP cancellation, and killing the MCP shim (gate, criterion 5)

- Builds: `adapters/mcp`: per connection, a wrapper around the reader and writer given to `Listen` that sets a `gone` flag before it returns any read error (EOF included) or write error. When a tool handler's request context ends before its `Wait` returns, the handler calls `Cancel` on its operation iff `gone` is unset and the session context (the one given to `Listen`) is still live; otherwise it returns and the operation runs on. Why a flag: `mcp-go` ends a request context in two cases the context cannot tell apart, a `notifications/cancelled` naming the request (`inflightCancels`, `server/server.go` `handleNotification`, which returns before any handler registered with `AddNotificationHandler`) and `Listen` ending (`cancelRequests`, `server/stdio.go`, once the input ends or fails); the wrapper sees the end of input before `Listen` does. A daemon shutdown ends the session context and cancels every operation itself (step 3). This is the thin layer ADR-0025 §Consequences allows, built on public API only: the streams passed to `Listen` (or the `SetContextFunc` method of the `*StdioServer`, to carry the flag in the context).

### Readings the steps take

Not questions: each follows from a cited document, and each is cheap to change. The owner may promote any of them to a question.

- `droidyard call` prints the response envelope on stdout and exits non-zero iff it carries `error` (ADR-0019 §3: the CLI "speaks the native capability envelope"; `docs/architecture/capability-api.md` §Error model: one shape everywhere).
- **`operation.wait`, natively and in the schema.** ADR-0020 §Operation capabilities: it returns "the `Outcome`" `{state, result | error, progress, blockedBy?}`; `docs/architecture/capability-api.md` §Operations and cancellation: "the same shape as the response envelope"; ADR-0020 §Adapter projections fixes the operation view for MCP only. Read together: (a) natively, the response envelope of an `operation.wait` call carries in `operation` the waited operation (`id`, `state`, `progress?`, `blockedBy?`) and in `result` or `error` that operation's own. The call itself is not an operation (ADR-0020: "`operation.*` calls themselves are not recorded"), so nothing else could fill `operation`. A rejection of the call itself, such as `OPERATION_NOT_FOUND`, is an `error` with no `operation`, like any rejection. (b) The golden `output` of `operation.wait` is its MCP projection, the operation view, as the golden `output` of a long-running capability already is; the native `result` is the waited operation's result, whose schema is the one `operation.capability` names. So A5 compares the MCP wire with the golden file, and the native envelope is checked by steps 3, 5 and 7. (c) By the first reading, `call operation.wait` exits non-zero when the waited operation ended `failed` or `cancelled`, and 0 when it is `completed` or still running at the deadline.
- `operation.cancel` returns an empty object, the projection of `Cancel(OpID) error` (ADR-0020 §Core primitives); callers read the outcome with `operation.wait`.
- `operation.wait` with `timeoutMs` omitted, on the native path, waits with no deadline, as an omitted `waitMs` does (`docs/architecture/capability-api.md` §Request envelope). The MCP adapter always supplies the budget.
- `system.health` `operations` counts operations not yet in a terminal state, the calling `system.health` operation excluded. The capability "reports whether the core is alive" (its description in `schema/capabilities.json`); in-flight work is the signal, while retained terminal records only reflect the retention window. No schema change: the field's type and name stay.
- **Adapter wiring** (`docs/architecture/core-runtime.md` §Adapter boundary; ADR-0025 §Consequences: adapters import `capability`, `event` and `artifact` only). The envelope's Go types live in `internal/capability`, next to `Error`. `cmd/droidyard` owns the wiring: it generates the schema bytes with `internal/schema` for `adapters/mcp`, dials the socket and sends the hello for `adapters/cli`, and registers the MCP handler with `internal/daemon`. No adapter imports `internal/schema`, `internal/daemon` or `internal/platform`.
- A result's MCP text rendering is its compact JSON. No per-capability renderer is documented, and the two shipped tools do not need one.
- The hello's `protocol` is the integer 1.
- The lock's `startTime` is the daemon's own clock at start. The lock identifies the holder for humans and `stop` (ADR-0021 §Locking), and a held `flock` rules out pid reuse; kernel start times matter for pid records (1c).
- `version` stays `0.1.0` when step 1 adds two capabilities: no version has been released to a consumer ("nothing is reachable by an agent yet", `docs/README.md` §Where the work stands).
- `droidyard status` exits 0 when a daemon answers and non-zero otherwise.

## Changes

- 2026-09-30, review round 1, before approval: steps 5 and 6 swapped. MCP cancellation (criterion 5, a gate) is now step 5 and the manual OpenCode run step 6, so a gate failure stops the milestone before owner or implementer time goes into a real-client run. Order only; no behaviour changes. ADR-0025 §Decision originally referred to "the plan's steps 4 and 6"; its step references were dropped the same day so a future reorder cannot leave it stale (ADR-0025, second `Amended:` line of 2026-09-30).
- 2026-09-30, during step 5, before verification: the step's gate passed, but a case its checks expose has no answer in the documents. When a session ends while its tool call is still in flight, the adapter cannot answer with a typed error — the closed code list has no code for "the session ended; the operation continues". Its provisional answer is an `isError` result whose text is plain prose, which does not match the error model (`docs/architecture/capability-api.md` §Error model). Put to the owner with two options: drop writes once the stream is gone, or add a `SESSION_*` code. **Resolved 2026-09-30: the owner chose to drop writes.** Once the stream wrapper sets `gone`, the session's writer drops everything, the answer to an abandoned call included; the prose answer is gone, no code was added, and the operation runs on, waitable from any session (step 5's (c) now also asserts that nothing is written after the input ends).
- 2026-09-30, during step 3, for the owner: with a socket path over `sun_path`, ADR-0019 §6's fallback `/tmp/droidyard-<uid>/droidyard.sock` is shared by every state root, and one holder can unlink another's live socket. Not exercised: the implementation follows the ADR path as written and the test suite binds only short state directories. A discriminating segment (a hash of the state root) would need an `Amended:` line on ADR-0019 §6; accepting the sharing needs the same. **Resolved 2026-09-30: the owner chose the hash; ADR-0019 §6 amended (third pass).** `internal/platform` now falls back to `/tmp/droidyard-<uid>/<first 12 hex of sha256(symlink-resolved state root)>/droidyard.sock`, and the daemon refuses a socket directory, or its parent, that is not a real directory of this user, and a parent that everyone may write to.
- 2026-09-30, during step 8: `droidyard mcp --wait <duration>` is a flag of the shim, which holds no MCP logic, while the budget is applied by the adapter inside the daemon; the only channel between them before the MCP bytes is the hello, whose shape ADR-0019 §7 fixes as `{protocol, version, client, root?, cwd}`. The hello gains an optional `waitMs` (absent: the 20 s default), recorded by ADR-0019's fourth `Amended:` line of 2026-09-30. Protocol stays 1: the field is optional and shim and daemon are one binary.
- 2026-09-30, verification of the milestone, blocking finding: `Holder`'s probe (a `LOCK_SH|LOCK_NB` on `daemon.lock`, taken by `status` and `stop`) conflicted with `Acquire`'s `LOCK_EX|LOCK_NB`, so a `serve` starting during a probe logged "lost the lock" and exited although no daemon existed, and an auto-starting shim then started no other (reproduced with a `perl`-held `LOCK_SH`; step 3 had noted the hazard, step 9's race did not expose it). Fixed in `Acquire`: on `EWOULDBLOCK` it retries for 100 ms (`probeGrace`) before concluding; a probe holds the lock for microseconds, a daemon for its life. Caught by `TestAcquireOutlastsAHolderProbe` (in process, real `flock`, level 4) and `TestServeStartsThroughAProbe` (a real `serve` started under a held `LOCK_SH`, released 20 ms after it opens `daemon.lock`, level 5); both fail with the grace set to 0. A losing `serve` now exits about 100 ms later than before.
- 2026-09-30, verification of the milestone, visible behaviour: socket paths are now derived from the canonical state root (symlinks resolved, components in their on-disk case), so they carry the canonical spelling, such as `/private/tmp/…` where `DROIDYARD_STATE_DIR` says `/tmp/…`, in the lock's `socket` field, in `serve`'s log lines and in client error messages. Every spelling of one root reaches the same socket and makes the same `sun_path` fallback decision (ADR-0019 §6; ADR-0021 §Layout). Caught by `TestSpellingsOfOneRootShareOneSocket` and `TestCaseOfARootIsTheOnDiskCase`.
- 2026-09-30, verification of the milestone, visible behaviour: `droidyard call --detach` prints the operation id and exits 0 whatever state the first snapshot shows, `failed` and `completed` included; the caller reads the outcome with `operation.wait` (ADR-0020 §Adapter projections, CLI row). Before, a snapshot already terminal printed the envelope. Caught by `TestDetachPrintsTheIDWhateverTheState`.
- 2026-10-02, after close, from the cross-family review (GPT-5.6 over `schema/capabilities.json`): the operation view's `operationId`, `capability` and `state` are now `required` in every view schema (the golden file gains one `required` list on `operation.wait`; no shipped capability is long-running), and `operation.wait`'s descriptor lists `OPERATION_CANCELLED` beside `OPERATION_NOT_FOUND`, because the waited operation's error is forwarded. `capability-api.md` §Operations and cancellation and ADR-0020's second `Amended:` line record it.
