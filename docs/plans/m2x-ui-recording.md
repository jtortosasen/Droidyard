**The owner should see:**
- **Record** and **Stop** in the UI events panel for the toolbar's device, local or lent. While it runs, the daemon stores the full dump (`device.uiDump`'s document) each time the screen changes, skipping one identical to the previous, with every `device.uiEvents` event in between.
- One file per recording, `<id>.jsonl`: header, then event, gap, dump, missed and end lines, each dump with its device time and whole XML. The panel lists the kept recordings with Download and Delete. An agent uses `device_recordUi`, `device_stopUiRecording` and `droidyard artifact cat <ref> > rec.jsonl`; the XML never passes through the model.
- A lent phone works the same: `device.uiDump`, `device.uiEvents`, the UI events panel and recordings on `<remote>/<serial>`. A remote recording runs on the host; when it ends, the client copies it whole and the host deletes its copy.
- A recording belongs to the daemon: it outlives the session that started it, ends by Stop, a bound, the device leaving, a reader that cannot be restarted, the lease ending or the daemon's exit, and says which. The UI events panel no longer stops `failed` while another call holds the reader (R3).
- While recording, the reader holds the device's one `UiAutomation`: a UiAutomator, Appium or Maestro run cannot start beside it (Q9: the owner uses none).
- A dump of Chrome taken before it has built its page (it does so within seconds of a reader connecting) says so in a warning, so a parser knows to retry.
- One minor API version, 0.33.0 (or the next free minor).

### 2. A patient events reach (R3)

## Design questions

None blocks the plan: Q1–Q8, Q10 and Q11 are Delegated, and the main session writes ADR-0113, ADR-0114 and ADR-0115 from them after step 1 (as m2w wrote ADR-0110–0112); where a step and an ADR then differ, the ADR wins. Q9 is answered by the owner.

- **Q1. Capture trigger and rate (ADR-0113).** Recommended: one rule on the ring: a dump at start, then whenever an event came after the previous dump's request and the gap since that dump ended has passed, and one at stop; so a burst is dumped as fast as the gap allows and its settled state is always stored. Gap 100 ms (S4 kept it), doubled after each identical dump up to 2 s; no exclusion rule (S2); a 5 s pause after `busy` (S1). Identical by SHA-256: counted in `unchanged`. Each `dump full` first waits up to 500 ms for quiet (unchanged), so during an animation a stored state leans toward a pause and a dump holds the lock up to about 0.5 s plus its traversal. Lost states are shown: `time`, `ms`, `waitedMs`, events between dumps, `missed`, `lockWaits`. Rejected: a fixed-interval sampler; a dump per event; a dump only after settle; dropping the idle wait (a reader change and its gates).
- **Q2. Bounds, ends, lifetime (ADR-0113).** Recommended: `maxSeconds` 10–3600 (900), 10,000 dumps, 512 MiB; one recording per device. Ends: `stopped`, `maxDuration`, `maxDumps`, `maxBytes`, `deviceGone`, `failed`, `daemonExit`; a reader restart is a gap; the reader cannot exit idle while polled (ADR-0111 §4). A daemon-owned job, as a detached share (ADR-0108), bounded by `maxSeconds` with no session state (ADR-0019 §Sessions, ADR-0010). Rejected: ending with the starting session; several recordings of one device.
- **Q3. Where and in what form (ADR-0113; amends ADR-0021 §Layout, ADR-0012 §Durability classes, ADR-0110 §2 in part).** Recommended: `<state>/recordings/<id>/` with `recording.json` and `timeline.jsonl`, a durable artifact `r.<id>`, `application/x-ndjson`, untrusted by class. The first durable store of device text on the host (ADR-0110 §2 "the daemon writes no host file"), kept because the owner wants spans for his parsers: 0600 under the 0700 root, deleted with its record, no age limit. Lines: `{kind: "recording", id, device, invisible, hostStartedAt, deviceStartedAt, format: 1}`; `{kind: "event", …}` (`device.uiEvents`'s fields); `{kind: "gap", reason, dropped?}`; `{kind: "dump", n, time, ms, waitedMs, trigger: start|change|stop, nodes, foreground, bytes, sha256, unchanged, warning?, xml}` (`warning`: Chrome's page not exposed yet, step 5); `{kind: "missed", time, reason}`; `{kind: "end", time?, hostTime, reason, cause?}`. Write order; `time` device clock (a dump is the screen at an instant within `[time, time+ms]`); `hostTime` the host's. One file is the bundle. Retention 50 and 2 GiB of ended ones. Rejected: a zip (a byte mode in `artifact.read`, a fourth type under rule 8, a browser zip writer or a new route); an artifact per dump; the workspace's `artifacts/` (devices are global); ephemeral artifacts.
- **Q4. The contract (ADR-0113).** Recommended: `device.recordUi` (a short command starting the job), `stopUiRecording`, `uiRecordings`, `watchUiRecordings` (web), `deleteUiRecording` (human only); one code, `DEVICE_UI_RECORDING_ACTIVE`; API 0.33.0; three MCP tools (budget by its rule). The stop cancels no operation, so ADR-0020's "no domain-specific cancel" is untouched; who may stop is ADR-0101's reach rule on the starting origin, its chat id kept on disk and never published (ADR-0088 §4), only `startedBy {client, session?}` (ADR-0048 §1). Rejected: a long-running `recordUi` (an MCP start blocks 20 s, an interrupt cancels the recording, a cross-session stop is a domain cancel against ADR-0101); an `action` parameter (none exists; `capability-api.md` §Discriminated tools over overloaded ones); polling from the web.
- **Q5. The lock and the stream (ADR-0114; amends ADR-0112 §3 in part).** Recommended: the recorder holds `readerClient.lock` only per dump (200 ms wait), takes no `Resource`, uses the persistent reader only, pauses after `busy` past the slowest abandoned dump. A patient reach (streams, the recorder) treats a held lock as an empty tick, failing only when its own restart fails; calls keep ADR-0111 §8. Rejected: holding `dumpKey` for the span; dumping on the second worker without the lock; a busy bound (any value below an act's 60 s host bound fails a stream behind a legitimate holder).
- **Q6. Untrusted and policy (ADR-0113).** Recommended: `recordUi` authorizes as every device call (ADR-0015 §4; a remote id by the client's own policy first, ADR-0100 §2); stop, list, watch and delete touch only daemon records. The timeline is untrusted by class; summaries and watch events carry no device text; the web renders none. Dumps are the active window only (ADR-0110 §4) and events carry no notification text (ADR-0111 §3).
- **Q7. The web (ADR-0113).** Recommended: Record/Stop and the kept list in the UI events panel over `watchUiRecordings`; no viewer.
- **Q8. Text over `GET /v1/artifacts/{id}` (no new ADR).** Recommended: serve text as ADR-0012 and rule 8 already say, whole or by `Range`; refuse a growing one with today's 400 rather than add the growing header (a new ADR-0024 identifier). Rejected: browser paging (an Activity row per 256 KiB).
- **Q9. A recording and the owner's tests — answered by the owner, 2026-10-21:** "No voy a usar ni UiAutomator, ni Appium ni Maestro con droidyard. Droidyard está pensado para sustituirlos." A recording holding the device's one `UiAutomation` for its span is accepted; the descriptions and the skill keep one sentence saying a UiAutomation-based runner cannot run beside it.
- **Q10. The UI reads lent (ADR-0115; supersedes in part ADR-0099 §2, ADR-0110 §6, ADR-0111 §9, ADR-0112 §1).** m2w's Q9 left them unlendable, a Delegated call made without the owner's use case; the owner's standing rule makes lending the default. Recommended: `uiDump` relayed with its artifact fetched (`application/xml` added to the peer route's types), `uiEvents` relayed plain with the host's cursor passed through, `watchUiEvents` relayed as `watchLogs` with ADR-0106's four streams per link and device on the host; `DEVICE_OCCUPIED` in their errors, and a peer's stream ends with its lease and counts as activity (ADR-0104 §3, §4).
- **Q11. Recording a lent device (ADR-0115; supersedes ADR-0104 §3 in part).** Recommended: the recorder runs on the host that owns the device; start, stop, list and watch are relayed; the client copies the timeline once the recording ends and the host then deletes its copy. A peer's recording takes and holds the lease (it counts as an open stream for §3's idle rule) and ends with it (§4: link, unlending, device leaving, `session.release`), `deviceGone` with the lease's cause; the timeline stays on the host until the client copies it. A peer sees, stops and deletes only its own (ADR-0101's peer branch); the host's UI and CLI see and stop all; a host MCP agent cannot stop a peer's. On the host a peer keeps at most 10 recordings and 1 GiB. For a peer, stop and a device-filtered list run `leaseFor` without adb, so they hold the lease as any device call. The peer route serves a peer its own finalised timelines by `Range` (409 while not finalised, 404 for anything else, deleted ones included: no existence oracle); a peer's `artifact.read` never reaches a timeline. The client copies to a `.part` file renamed only after the SHA-256 matches, its own reference reading `growing` until then, and adopts at link up any ended recording of its own the host holds that it has no record of. Rejected: a recorder on the client over relayed `uiEvents` polls and `uiDump` calls (ten host operations a second in the host's audit, a dump's artifact fetched per change over the VPN); a recording that outlives the lease (another peer could take the device while it records the first's session; ADR-0104's one person at a time); the client reading the host's growing timeline live (a remote artifact class; counts suffice while it runs).
