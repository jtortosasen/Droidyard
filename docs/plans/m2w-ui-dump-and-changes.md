- `device_uiDump` (MCP and UI): every node of the screen, no byte cap, every attribute the reader can read, in an XML that a `uiautomator dump` parser reads unchanged; optionally every window and the hidden children. ## Acceptance

- [ ] A1. `device.uiDump` returns an `application/xml` artifact holding every node of the active window, layout-only ones included, with no byte cap below the 8 MiB read cap (over it: an error, never a cut document); every attribute of a real `uiautomator dump` of the same screen is present on the same nodes with the same value, plus the extras of Q3; `windows: true` adds every window as a root node, `invisible: true` the children not visible to the user. Source: R1; Q1–Q3. Proven by: steps 3, 4, 8.
- [ ] A2. The dump is read with `artifact_read` in whole-line pages, and `droidyard artifact cat <ref>` writes it byte for byte; Python's ElementTree and the daemon's own `uiautomator dump` parser (`parseDump`) read it unchanged. Source: R1 ("a file the agent parses with code"); Q2. Proven by: steps 4, 8.
- [ ] A3. `device.uiEvents` returns the events after a cursor, oldest first, none twice and none skipped across calls; a toast shown between two calls is reported with its text; a notification is reported with no text; at most `max` per call, with `more` when more wait. Source: R2; Q4–Q6. Proven by: steps 5, 6, 8.
- [ ] A4. A reader start, restart or idle exit, and a ring overflow, between two calls are reported as a `gap` with its reason (and the dropped count for an overflow); never silently. Source: R2; Q5. Proven by: steps 6, 8.
- [ ] A5. `waitMs` with `until: change` returns at the first new event, with `until: settle` once no event came for `quietMs`, at most 20 s; a wait never delays a `uiTree`, `uiDump` or action on the same device. Source: R2; Q7. Proven by: steps 6, 8.
- [ ] A6. The UI events panel shows the toolbar device's events within 1 s while it is visible, and stops polling when hidden. Source: R2; Q8. Proven by: steps 7, 8.
- [ ] A7. A physical device the policy refuses gets `DEVICE_NOT_ALLOWED` from all three capabilities before any `adb shell`; a remote id gets `DEVICE_NOT_FOUND` with no host call; `device.watchUiEvents` is not an MCP tool; no policy reaches MCP. Source: ADR-0015 §4, §6; ADR-0010; Q9. Proven by: steps 4, 6, 7.
- [ ] A8. The reader's dex on the device is trusted only when its SHA-256 is the pinned one; gates G1, G2, G3 and G5 pass on the final digest. Source: R3, R4; ADR-0029 §Decision. Proven by: steps 2, 8.
- [ ] A9. One minor version with exactly the schema diffs steps 4, 6 and 7 declare; the MCP tool list gains exactly `device_uiDump` and `device_uiEvents`. Source: `capability-api.md` §Discovery and versioning; ADR-0036. Proven by: steps 4, 6, 7.

### 4. `device.uiDump` and `droidyard artifact cat` (the first end to end)

- Builds:
  - `internal/domain/device/uidump.go`: `device.uiDump {device, windows?, invisible?}` → `{device, dump: ArtifactRef, nodes, windows, foreground, warnings?}`; kind query, global, stateless, idempotent, not long-running (the read chain's 22 s deadline plus the 20 s queue bound stays under 60 s, ADR-0020), since `0.32.0`; `Resource` `dumpKey(device)`, shared with `uiTree`; `authorize` = `adb.authorize` (**not** `adb.plain`: not lendable, Q9); `uiTree`'s error list. The artifact: `application/xml`, untrusted, producer `device.uiDump`, owner `OwnerOf(origin)`. A document over `dumpOutputCap` fails `DEVICE_UI_DUMP_FAILED` naming the cap, with no artifact. `nodes` and `windows` are counted by `parseDump`, so a document it cannot read is a failed dump; `foreground` is the package of the root marked `window-active="true"` when there are several roots (`getWindows()` lists the status bar or the IME first), else the first root's. Not in the `--tools core` profile (ADR-0036 §4): it is not on the golden path. A text rendering (ADR-0036 §2): the ref, bytes, counts, the quoted foreground, and how to save it. A description within ADR-0036 §1's rule.

It pages `artifact.read` over the daemon's socket, as every CLI call does, rather than `GET /v1/artifacts/{id}`, which needs the UI's per-launch token. The daemon writes no host file; the caller's shell chooses where the bytes go.

## Design questions

None blocks. Each is Delegated: the main session applies the recommendation and writes the ADR named in Contract, from step 1's note. Q5 and Q11 are flagged to the owner.

- **Q1. A capability, not a mode of `uiTree` (ADR-A).** Recommended: `device.uiDump`. `uiTree`'s contract is compact, ref-bearing and capped at 40 KB (ADR-0036's token budget); a mode would add parameters to the most-called tool's schema and give it two result shapes. Rejected: `uiTree {full: true}`; raising the cap.
- **Q2. Delivery as an artifact, saved by the CLI (ADR-A).** Recommended: an ephemeral `application/xml` artifact (ADR-0012), one element per line so `artifact_read` pages it by whole lines, and `droidyard artifact cat <ref>`, which writes the bytes to stdout for the agent's shell to redirect: the XML reaches a parser without passing through the model, and no result names a host path. Cap: the 8 MiB read cap, beyond which the call fails rather than cut a document. Rejected: inline text (tokens); writing into the workspace (a file write from a device tool, after 2j moved file tools off MCP, and a workspace scope for a device read); an artifact path in the result (ADR-0012).
- **Q3. The format (ADR-A).** Recommended: a superset of `uiautomator dump`: `<hierarchy rotation>` and `<node>` with its attributes, names and order, always written; extras appended, only when non-default: `editable`, `visible-to-user`, `state-description`, `error`, `heading`, `pane-title`, `tooltip`, `input-type`, `max-text-length`, `actions` (standard action names, comma-separated), `custom-actions` (labels, newline-separated, escaped), `collection-rows`, `-columns`, `-hierarchical`, `-selection-mode`, `collection-item-row`, `-column`, `-row-span`, `-column-span`, `-heading`, `-selected`, `range-type`, `-min`, `-max`, `-current`, `text-links` (`start-end[=url]`, space-separated, the URL's spaces as `%20`), and cheap flags (`dismissable`, `multi-line`, `content-invalid`, `context-clickable`, `important`); every window as a root `<node>` under the one `<hierarchy>` (as androidx UiAutomator's own window dump does), carrying `window-id`, `-type`, `-layer`, `-title`, `-active`, `-focused`, `-display-id`. **SystemUI rule** (applies only if step 1 S3 finds notification text in a non-active window): with `windows`, the nodes of a `com.android.systemui` window that is not the active one carry no `text`, `content-desc`, `hint`, `tooltip`, `state-description` or `pane-title` (empty, as `uiautomator dump` writes an absent value), so the dump reads no more of a notification than today's active-window `uiTree` already does when the user opens the shade. A full dump that passes the 2.5 s bound fails with a cause of its own, never ADR-0034 §1's "the app did not answer". Rejected: child elements for collection or range data (a parser walking children would read them as nodes); a `<window>` wrapper (it breaks `hierarchy/node` parsers); JSON.
- **Q4. Where the events live (ADR-B).** Recommended: in the reader, a bounded ring on the device. It records with no host connection open, so a toast between two calls is kept even when nobody polls; the daemon reads it on demand. Rejected: a ring in the daemon fed by a held reader connection (events are lost whenever no connection is held, and a held connection per device is a new lifetime to manage); `logcat` (accessibility events are not logged).
- **Q5. Cursor, gaps and privacy (ADR-B). The privacy half is the owner's.** Recommended: the cursor `<instance>.<seq>`; gaps `readerStarted`, `readerRestarted` (a restart or the 30-minute idle exit), `overflow` with `dropped`; an `events` request is a read for ADR-0030's idle timer (its text says "without a read"; the code's "only a dump" was an implementation choice), so a watching panel keeps the reader while visible, and an unplugged device still releases `UiAutomation` after 30 minutes. **Privacy**: in the events, a toast's text is kept; a notification event's text is never read, on the device, in this milestone, and no other event carries text; the agent reads content with `uiTree`. In the dump with `windows`, Q3's SystemUI rule keeps notification text out of non-active SystemUI windows if step 1 finds it there; an open shade, being the active window, is read as `uiTree` reads it today. Rejected: a call parameter turning notification text on (the agent would grant itself a person's messages and codes); notification text with a redaction heuristic (ADR-0015 §1 refuses heuristics). **For the owner:** whether a switch should ever let notification text through, and if so as a human-only policy setting (ADR-0015 §6).
- **Q6. The event shape (ADR-B).** Recommended: `{time (device clock, RFC 3339, as device.logs), type, package?, class?, window?, count?, text?, changes?}`, types `windowState`, `windowContent`, `windows`, `textChanged`, `focus`, `scroll`, `click`, `selected`, `toast`, `notification`, `announcement` (no text). No refs: an event has no snapshot; `uiTree` mints them. Coalescing on the device: content, scroll and text events of the same type, package and window within 250 ms (step 1 may move it) fold into one with a count, but never into an entry an `events` answer has returned (the answer seals it), so a reader past its cursor loses no fold. Rejected: folding into returned entries (their later counts are invisible to every cursor past them); refs or node ids (an extra query per event, on the thread that must not block); the event's source subtree.
- **Q7. The wait (ADR-B).** Recommended: `waitMs` ≤ 20,000 with `until: change | settle` and `quietMs`, polled by the daemon every 100 ms; `settle` means no event for `quietMs` counted from the later of the newest event after the cursor and the call's start, so a quiet screen settles at once after `quietMs`; not long-running (20 s plus at most two bounded recoveries, 42 s, stays under ADR-0020's 60 s), and no resource key, so it never queues a read or an action; the read lock is taken only to recover a dead reader, for at most 2 s. Rejected: a long poll held on the device (a thread per waiter on the reader); reusing the reader's `waitForIdle` (bounded at 500 ms and blind to which events came).
- **Q8. The web panel in this milestone (ADR-C).** Recommended: yes, as the last code step. The owner asked for it, and it adds no new risk: the same ring and cursor, polled every 250 ms by a streaming capability (one operation per stream, where browser polling would put an operation per poll in Activity). The milestone can stop before it, with the agent path proven.
- **Q9. Not lendable in this milestone (ADR-A, ADR-B).** Recommended: the three capabilities are not `Lendable`, so ADR-0099 §2's list is unchanged and a remote id is `DEVICE_NOT_FOUND`. Lending `uiDump` and `uiEvents` is cheap (`adb.plainThen`, with the artifact fetched as `device.screenshot`'s), but extends a decided peer surface; it goes to a register row.
- **Q10. "A fixed 300 ms settle after every tap …".** Its `Closed by` column says 1n, and `ui-automation.md` §Sequence and timing says there is no fixed settle (plan m1n D2). Nothing to do; its `Work` is not set. The settle wait of Q7 is for agents between their own calls, not inside `tapElement`.
- **Q11. Tree diffs between reads (the owner's, since the gather put it in).** Events say what kind of change happened and where, not what a tree's nodes became; a diff of `uiTree` against an earlier snapshot is a contract change to the most-called tool, with its own decision on node identity across snapshots (the identity `ref` resolution uses does not survive a text change). Recommended: leave it out of 2w and the row as it is; an alternative is a ninth step, `uiTree {since: snapshot}` returning only new or changed nodes and the removed refs, decided in its own ADR.

## Changes

Changes after approval: date, what changed, why, and the ADR if the change touches the design.

- 2026-10-20, step 1 (the spike, [research note](../research/spike-ui-dump-events-2026-10.md)). S1, S2, S4, S5 and S6 pass on API 31 and 36. **S3 fails**: `getWindows()` lists interactive windows only (with a dialog open, the app window under it is not listed), and during a heads-up a SystemUI window holds the notification's text. By S3's own rule, Delegated: **`windows` leaves the milestone**. `device.uiDump` reads the active window only; the reader's request is `dump full [invisible]`; the result has no `windows` field; Q3's window attributes and its SystemUI rule are dropped; ADR-A records why. R1 closes in part, and its "every window" part becomes a register row with S3's two facts. A1 loses its `windows: true` clause. **S4**: the reader already reads every node `uiautomator dump` reads (not-important views are included at connect); on API 31 two bounds differ from `uiautomator dump` (the root and the navigation bar background: the reader writes the real display's, `uiautomator` the app area's), so A1's "same value" excepts `bounds` on those two nodes on API 31; on API 36 the two dumps are identical. For Q4: the framework already throttles content changes to at most 10 a second (a 20 ms ticker), and the notification event carries no text on either level. `collection-item-*` and `getExtras()` returned nothing on formapp; `invisible` adds the scroll content below the fold (an INVISIBLE view is never exposed).
- 2026-10-20, steps 3, 4, 5, 6, 7: ADR-A, ADR-B and ADR-C are written as [ADR-0110](../adr/0110-full-ui-dump.md), [ADR-0111](../adr/0111-ui-events-between-reads.md) and [ADR-0112](../adr/0112-ui-events-stream-and-panel.md); where a step's text and an ADR differ, the ADR wins. Step 3: the reader's request is `dump full [invisible]` (no `windows`, no `getWindows()`, no interactive-windows flag, no SystemUI rule); its level-5 fixtures are `reader-full-widgets-api{31,36}.xml` and `reader-full-invisible-widgets-api{31,36}.xml`; the dialog check reads the dialog's window as the active one; `hidden` (INVISIBLE) is absent from every dump, and `invisible` is checked on the scroll content below the fold instead; `collection-item-*` is not expected on formapp's ListView rows (absent on both levels in step 1). Step 4: `device.uiDump {device, invisible?}` → `{device, dump, nodes, foreground, warnings?}`; `foreground` is the root's package.
- 2026-10-21, steps 5, 6: the reader caps an event's package and class at 128 characters (silently, as the toast text at 512), so 200 entries stay under the 1 MiB `events` read whatever an app names its classes; step 6's description says `package` and `class` are capped. A window id is any int32 (the platform's -2 and -3 included).
- 2026-10-21, step 6: the rendering writes a fold count as `xN`, not `×N` (the text builder quotes any non-ASCII word); `TestUIEventsWaitChange` allows 250 ms after the event, not 150 ms (the 100 ms poll plus a loaded machine's margin); a cursor of this reader's instance but past its newest event is `REQUEST_INVALID_PARAMS` (ADR-0111 is silent; no legitimate client can hold one, since a restart or a reboot draws a new instance). Found at level 5: during a fling each scroll event is followed by a content change, and ADR-0111 Decision 2 folds only into the newest entry, so a fling's scrolls stay one entry each; a burst of one type (the spinner) folds. A register row.
