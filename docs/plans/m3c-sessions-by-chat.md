## Design questions

Delegated by the owner's brief ("decide; refine with reasons"): the main session applies the recommendations and writes ADR-0127 before step 2; step 1 may run first. If step 1 contradicts a draft, the steps it touches are redrafted under Changes first.

- **Q1. The contract.** The documents say: ADR-0083 §1 (`session.watch`, live MCP sessions only), ADR-0088 §4 (the chat id is never published). Recommended: a new capability `session.chats` (read-only, stateless, global, audience human, so off MCP), the shape in step 2: the store's chat id published, `session` the live session's id when joined, `sources` per store, `truncated`. The UI calls it on start, after `session.state` changes and every 30 s (working default). Publishing the chat id supersedes ADR-0088 §4 in part: the id is the file name or directory name in the user's own store, readable by any process of the user, and ADR-0094 §9 says occupation is not a security boundary; the capability stays off MCP. Rejected: **chats inside `session.watch`**: a stream of live connections would carry rows read from files that change on no event of the daemon's, and mix two lifetimes, as ADR-0083 rejected for workspaces; **a streaming `session.watchChats` over a watch of the stores**: an OS watch of directories that grow by many MB an hour for a panel a 30 s read serves; **the join in the browser by chat id on `session.watch`**: it publishes every live session's chat id on a stream for the same result.
- **Q2. What is read, and how far.** The documents say: nothing on chat stores; the owner's condition. Recommended: the chats of the projects the daemon knows (the index's main trees, at most 50) and their live linked worktrees (ADR-0089 §2, no git), in the directories the clients file them under; Claude Code as in step 2 (the windows, the keys, the place from the directory that holds the transcript, since it moves with its working directory, the `cwd` only guarding the lossy encoding, the title precedence after Orca's reading, never the first prompt); **a chat is what the client's own resume list shows**: a transcript with no conversation line is left out, and the headless `sdk-cli` runs are listed unless step 1 (f) shows `claude --resume` leaves them out, in which case they are left out too; Cursor as in step 4; 30 per client and project, 200 file reads and 2 s a call, 120-character titles, a cache on size and mtime (working defaults). Rejected: **every chat in the stores**: the owner asked for their projects, and the other projects' chats include repositories that must not be read; **a full parse** (Orca's): 124 MB transcripts read every refresh; **the first prompt as the fallback title**: message content, outside the owner's condition; **chats of removed worktrees** (a prefix match on directory names): their resume command no longer runs where they were, and the encoding is lossy.
- **Q3. SQLite.** The documents say: ADR-0068 §1 builds with `CGO_ENABLED=0`; ADR-0021 rejected SQLite for its own state "at the cost of cgo or a multi-megabyte pure-Go driver"; ADR-0005 reuses platform tools. Recommended: the `sqlite3` command, as `git` and `adb` are run: `-readonly -safe -init /dev/null -json`, a constant query, a 3 s kill of its group, a 4 MiB cap, `mode=ro`, and `immutable=1` only on a WAL db with no `-wal` or `-shm` beside it (closed), so nothing is created there; absent, the Cursor stores are a `failed` source. macOS ships it; Linux may not have it, a register row. Rejected: **`mattn/go-sqlite3`**: cgo, against ADR-0068's one-runner cross-compile; **`modernc.org/sqlite`**: a multi-megabyte transpiled dependency to read a few keys, ADR-0021's objection; **an own reader of the file format**: B-trees, overflow pages and WAL frames, for one table; **copying the db first**: hundreds of MB, and a copy without its `-wal` misses the live rows.
- **Q4. The panel.** The documents say: ADR-0083 §2 (each project with its sessions and worktrees), ADR-0048 §3 (rows from operations), m2d D30 (the "You" row). Recommended: Projects keeps the project and worktree rows (opening, selecting, Release, Remove); a Sessions section below groups Client → Project → chat as the owner drew it; a connected chat is one row with its session's state; an unclaimed live session is a row; no "You" row and no operation-only rows (the user's operations stay in Activity); the panel's labels numbered among the rows listed now, while Activity, the build status and the devices keep a per-tab label never renumbered, so two agents never share a name there (ADR-0048 §Alternatives); a name no client claims, a peer's link included, under "Other"; 8 per project and "N more"; Copy of the resume command for Claude Code and cursor-agent. Supersedes ADR-0083 §2 in part and ADR-0048 §3 in part, and replaces D30's "You" row. Rejected: **the whole column as Client → Project → chat**: a project with no chat could not be opened or selected, and worktree rows, Release and Remove would lose their place; **Project → Client → chat**: not the owner's order; **a launch button** for resume: ADR-0004, Droidyard launches no client.
