## 1. Agent state detection

### 1.1 State vocabulary (Orca)

- Row states: `working | blocked | waiting | done` (`src/shared/agent-status-types.ts:52`) [read]. There is no `idle` or `error` or `interrupted` row state at the top level:
  - `idle` exists only for subagent/child rows (`src/shared/program-status/agent-status-projector.ts:50-62`, subagent state `idle`) and as the dashboard bucket `idle` (`src/shared/dashboard-snapshot.ts:14`) [read].
  - "interrupted" is a flag on a `done` row: `interrupted?: boolean` (`agent-status-types.ts:139-141`) plus a turn verdict `mainAgent.outcome` in `success | failure | cancellation | superseded | interruption | unconfirmed` (`src/shared/agent-turn-outcome.ts:12-30`) [read].
  - "error" is `done` + outcome `failure` (OSC `error` -> `{state:'done', outcome:'failure'}`, `agent-status-projector.ts:122-123`; Claude `StopFailure` -> outcome `failure`, `src/shared/agent-hook-listener/providers/claude-events.ts:97-98`) [read].
- `waiting` = approval or question for a human (hook-derived). `blocked` = unnamed/auth block (OSC-derived; "Orca's hooks report approvals and questions as `waiting`; auth and unnamed blocks stay `blocked`", `agent-status-projector.ts:45-48`) [read].
- Dashboard buckets: `attention` (= `blocked` or `waiting`), `working` (+monitoring), `done`, `idle` (`src/renderer/src/components/dashboard/dashboard-card-bucket.ts:6-18`). The "Needs You" column is the `attention` bucket label (`src/renderer/src/components/dashboard-popout/AgentKanbanBoard.tsx:41-43`) [read].
- `sessionBoundary` flag on a `done`: an idle landing (SessionStart, manual compact) that must NOT fire completion notifications (`agent-status-types.ts:142`, `:193-197`; `claude-events.ts:51-81`) [read].

### 1.2 Claude Code: events Orca installs

Installed into `~/.claude/settings.json` (or the CLAUDE_CONFIG_DIR) (`src/main/claude/hook-settings.ts:50-52`) [read]. One command per event pointing to a managed shell script `~/.orca/agent-hooks/claude-hook.sh` (shared path, `src/main/agent-hooks/installer-utils.ts:104-106`) [read]. Each entry has `timeout: 10` seconds (`installer-utils.ts:49`, `hook-settings.ts:138-163`) [read].

Events (`src/main/claude/claude-managed-hook-events.ts:9-79`) [read]:

| Event | Matcher Orca writes | Why Orca registers it (source comment) |
|---|---|---|
| SessionStart | none | only signal a resumed/idle session emits before first prompt (:10-15) |
| UserPromptSubmit | none | new turn |
| Stop | none | turn end |
| StopFailure | none | "OpenClaude skips normal Stop hooks after API/model errors" (:24-29) |
| SubagentStart / SubagentStop / TeammateIdle | none | child rows; keep pane `working` while children outlive the lead (:30-45) |
| PreToolUse / PostToolUse / PostToolUseFailure | `*` | live tool readout (:46-59) |
| PermissionRequest | `*` | approval wait (:60-63) |
| PostCompact | none | a manual `/compact` ends idle with no Stop (:64-71) |
| SessionEnd | none; only installed for Claude >= 2.1.261 (`installFrom`, :74-79) | process-ending exit proof |

Deliberately NOT installed: `PreCompact` (fires before validation; an aborted compact would strand the pane as `working`, :64-67) and **`Notification`** (grep of the whole tree finds no Claude `Notification` registration; only Copilot/Grok use that name) [read]. So Orca detects "blocked" from `PermissionRequest` + `PreToolUse(AskUserQuestion)`, not from Claude's Notification hook.

Version gating: Claude 1.0.23..2.1.100 discard the WHOLE settings.json on an unknown hook name, so each event is written only for a Claude that knows it; first versions pinned (PermissionRequest 2.0.45, PostToolUseFailure 2.0.56, SubagentStart 2.0.43, TeammateIdle 2.1.33, PostCompact 2.1.76, StopFailure 2.1.78, SessionEnd 1.0.85) (`src/main/claude/claude-hook-event-versions.ts:5-23`) [read]. [inferred] Droidyard's `init` should do the same gating if it ever adds an event newer than the user's Claude.

Payload fields Orca reads from Claude hooks [read]:
- `tool_name`, `tool_input` (preview via `deriveToolInputPreview`), `tool_response` (PostToolUse text), `error`/`message` (PostToolUseFailure), `last_assistant_message` (Stop; falls back to reading the transcript at `transcript_path`) (`providers/claude-tool-fields.ts:10-64`).
- `agent_id`, `agent_type` (present only for subagent/teammate events) (`claude-events.ts:42, 168-223`).
- `tool_use_id` (pairing a PostToolUse to the pending question/approval, `claude-events.ts:154-166`).
- `source` on SessionStart: only `startup|resume|clear` land an idle `done` boundary row; a `compact` restart or unknown source returns null (`claude-events.ts:56-67`).
- `trigger == 'manual'` on PostCompact (`:124`).
- `is_interrupt` on Stop (`:94-95`), `background_tasks`, `session_crons` (turn-boundary inventory, `:100-106`, `:226-236`).
- `reason` on SessionEnd; process-ending reasons = `prompt_input_exit|logout|other|bypass_permissions_disabled` (`src/shared/agent-hook-listener.ts:33-38, 231-258`).
- `session_id` and `transcript_path` (resume metadata only, `agent-session-resume.ts:204-212`); `prompt` for the user prompt (`prompt-fields.ts:36-45`).
- Orca does NOT read `cwd` from Claude hook payloads (grep of `src/shared/agent-hook-listener` finds `cwd` only in Grok paths) [read]; it knows the worktree from `ORCA_WORKTREE_ID`.

### 1.3 Claude Code: state machine (Orca's mapping)

From `claude-events.ts:86-166, 225-342` [read]:

| Event | Orca transition |
|---|---|
| SessionStart (source startup/resume/clear, no agent_id) | row -> `done` + `sessionBoundary:true`; clears stale subagent roster, running-task, cron, background-task caches (:51-81) |
| UserPromptSubmit | -> `working`; resets prompt/tool caches (new-turn event, `provider-event-routing.ts:33-36`); a compact-continuation prompt is ignored (:108-110) |
| PreToolUse (not AskUserQuestion) | -> `working` |
| PreToolUse with AskUserQuestion tool | -> `waiting`, `interactivePrompt` = JSON of tool_input (:112-118, `interactive-tool.ts:44-60`) |
| PermissionRequest | -> `waiting`, `interactivePrompt = {approval:{tool,summary}}` where summary is command/file_path/path/url/pattern clipped to 200 chars (`interactive-tool.ts:22-36, 61-68`) |
| PostToolUse / PostToolUseFailure | -> `working` (this is what clears a `waiting` after the user approves/denies/answers; a parallel sibling's PostToolUse with a different `tool_use_id` does NOT clear a pending question, :156-166) |
| Stop / StopFailure | -> `done` (outcome `failure` for StopFailure; `cancellation` if `is_interrupt` or latched), but the pane stays `working` while background tasks/subagents/crons/owed task-notifications remain (:277-300, `resolveClaudePaneStatus`) |
| PostCompact trigger=manual | -> `done`, `sessionBoundary:true`; PostCompact auto -> ignored (:119-124, 325-332) |
| SubagentStart/Stop, TeammateIdle | roster update; re-emits lead state with child list (`claude-lifecycle-events.ts`) |
| Child (agent_id) PreToolUse/Post... | keeps child row live, never changes lead state, unless the child's own permission wait (:168-214) |
| SessionEnd with exit reason | row marked `agentPresence.ended`; leaves the row's last payload (`agent-hook-listener.ts:231-258`) |

Cancellation (Esc): per Orca's own comment "Current Claude sends NO hook on a cancel and no `is_interrupt` on Stop" (`claude-events.ts:87-91`), so Orca INFERS the interrupt from the Escape keystroke on the PTY correlated with a title glyph or OSC 7501 idle within 5 s / 1.5 s (`src/shared/claude-terminal-interrupt.ts:12-14`; `server-status-inference.ts:100-135`) and latches the verdict for 15 s against late tool-progress hooks (`src/shared/agent-hook-cancel-verdict-latch.ts:5`) [read]. This matches the Claude docs: "Stop does not run if the stoppage was caused by a user interrupt" [doc] https://code.claude.com/docs/en/hooks. Not usable by Droidyard (needs the PTY).

Detecting a permission prompt vs a question to the user (Claude) [read]: permission = `PermissionRequest` (immediate, no 6 s delay). Question = `PreToolUse` whose `tool_name` is the AskUserQuestion tool (Orca's comment: "newer builds can also report it as PermissionRequest", `claude-events.ts:112-117`). Orca never uses the `Notification` event.

### 1.4 Claude Code: official docs for the events Droidyard asked about

All [doc] https://code.claude.com/docs/en/hooks unless noted:
- **Common input fields:** `session_id`, `prompt_id`, `transcript_path` (may lag the in-memory conversation), `cwd`, `scratchpad_dir`, `permission_mode`, `effort{level}`, `hook_event_name`, `agent_id` (only inside a subagent or in-process teammate), `agent_type`.
- **Notification:** input `message`, optional `title`, `notification_type`; example `{"hook_event_name":"Notification","message":"Claude needs your permission","title":"Permission needed","notification_type":"permission_prompt"}`. `notification_type` values: `permission_prompt`, `idle_prompt`, `auth_success`, `elicitation_dialog`, `elicitation_url_dialog`, `elicitation_complete`, `elicitation_response`, `agent_needs_input`, `agent_completed`, `quota_auto_resume_fired|stale|disabled`. Timing: `permission_prompt` fires when the approval prompt "has waited about six seconds" (terminal timer starts at prompt, each keystroke resets it; Agent SDK `canUseTool` fires ~6 s after request regardless of typing); `idle_prompt` fires when Claude "finished responding about 60 seconds ago and you haven't typed since" and not while a background agent runs or while waiting for a usage limit; `elicitation_dialog` ~6 s inactivity. `agent_needs_input`/`agent_completed` fire for background sessions only while agent view is open. Notification hooks cannot block or modify; exit code and stderr ignored.
- **PermissionRequest:** input `tool_name`, `tool_input` (like PreToolUse), NO `tool_use_id`, `mcp_server` for MCP tools, optional `permission_suggestions[]`. Output `hookSpecificOutput.decision.behavior = allow|deny`; "If no hook decides, the normal approval flow continues"; in sessions that cannot show a prompt (background subagents non-interactive) with no deciding hook the call is denied. Exit 2 not honored for this event.
- **Stop:** input `stop_hook_active`, `last_assistant_message`, `background_tasks[]` (id,type,status,description), `session_crons[]`. Does not run on user interrupt; API errors fire StopFailure instead.
- **StopFailure:** input `error` (rate_limit, overloaded, authentication_failed, oauth_org_not_allowed, account_on_hold, billing_error, invalid_request, model_not_found, server_error, max_output_tokens, cloud_credential_error, unknown), `error_details`, `last_assistant_message` (the API error string). Output and exit code ignored. [Orca's claim that OpenClaude skips Stop on API errors is an Orca comment, `claude-managed-hook-events.ts:24-26`, [read].]
- **SubagentStart:** `agent_id`, `agent_type`. **SubagentStop:** `stop_hook_active`, `agent_id`, `agent_type`, `agent_transcript_path` (nested `.../<session>/subagents/agent-<id>.jsonl`), `last_assistant_message`, `background_tasks`, `session_crons`.
- **SessionStart:** `source` = `startup|resume|clear|compact|fork`, `model` (optional), `agent_type`, `session_title`; extra fields on resume/fork. **SessionEnd:** `reason` = `clear|resume|logout|prompt_input_exit|other` (`bypass_permissions_disabled` removed in v2.1.234); default budget 1.5 s (raised by per-hook `timeout` up to 60 s or `CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS`).
- **UserPromptSubmit:** field `prompt` (pasted text arrives expanded), `session_title` when custom-titled; exit 2 blocks.
- **PreToolUse/PostToolUse/PostToolUseFailure:** `tool_name`, `tool_input`, `tool_use_id`; Post adds `tool_response`, `duration_ms`; Failure adds `error` (string; Bash usually `Exit code N`), `is_interrupt`, "Cancelling a running tool doesn't fire this hook"; Failure does not fire for validation errors or permission denials.
- **Exit semantics:** exit 0 + JSON stdout parsed; exit 2 blocks (blocking events); other non-zero = non-blocking error "hook error" notice, action proceeds; "Empty stdout with exit 0: success with no decision". Default timeouts: 600 s command/http/mcp_tool, 30 s prompt, 60 s agent; 30 s for UserPromptSubmit. `onFailure:"block"` exists from v2.1.295.
- **Env:** `CLAUDE_PROJECT_DIR`, `CLAUDE_ENV_FILE` (SessionStart/Setup/CwdChanged/FileChanged only). `CLAUDE_CODE_SESSION_ID`: not in the hooks page; [secondary] changelog v2.1.132 "Added CLAUDE_CODE_SESSION_ID environment variable to the Bash tool subprocess environment, matching the session_id passed to hooks" (via https://claudeissues.com/issue/56879-docs-environment-variables-claude-code-session-id-not-documented-in-env-vars-ref); whether hook commands also inherit it was NOT confirmed (OPEN-2).

### 1.5 Cursor: events Orca installs and the state machine

Installed into `~/.cursor/hooks.json` with `version: 1` and top-level `command` on each definition, each with `timeout: 10` (`src/main/cursor/hook-service.ts:12-14, 205-215`; `installer-utils.ts:77-79`) [read]. The Cursor docs lists the same `~/.cursor/hooks.json` as the user location [doc] https://cursor.com/docs/hooks.

Events (`src/main/cursor/hook-events.ts:1-12`) [read]: `beforeSubmitPrompt, stop, preToolUse, postToolUse, postToolUseFailure, beforeShellExecution, beforeMCPExecution, afterAgentResponse`. Comment: "Exclude process-boundary session hooks, which can reset the submitted-turn prompt cache" - so `sessionStart/sessionEnd` are NOT installed (though the normalizer handles them, `cursor-events.ts:19-33`, and `isNewTurnEvent('cursor', ...)` lists `sessionStart`, `provider-event-routing.ts:65-66`).

State machine (`src/shared/agent-hook-listener/providers/cursor-events.ts:16-67`) [read]:
- `beforeSubmitPrompt`, `sessionStart`, `preToolUse`, `postToolUse`, `postToolUseFailure`, `beforeShellExecution`, `beforeMCPExecution` -> `working`. Source comment: shell/MCP "fire on every invocation (pre-execution gates, not just approval); treat as working to avoid waiting-notification spam" (:24).
- `afterAgentResponse` -> `done` if the previous row was already a cursor `done` (late text enrichment), else `working` (:28-31).
- `stop` / `sessionEnd` -> `done`; `interrupted:true` when `stop.status` is a string other than `completed` (docs: `completed|aborted|error`) (:47-52).
- **Cursor never produces `waiting`/`blocked`** in Orca. Orca conclusion: no hook event reliably says "blocked on approval". [doc] Cursor docs "don't define a specific event that signals the agent is waiting for approval"; the nearest thing is `permission:"ask"` as an OUTPUT value for `beforeShellExecution`/`beforeMCPExecution`; `preToolUse` accepts `ask` but "doesn't enforce it", `subagentStart` treats it as deny.

Fields Orca reads from Cursor payloads [read]: `tool_name`, `tool_input`, `tool_output` (postToolUse), `error_message`/`error` (failure), `command` (beforeShellExecution; tool name forced to "Shell"), `tool_name` + `tool_input|command|url` (beforeMCPExecution), `text` (afterAgentResponse), `status` (stop), `prompt` (beforeSubmitPrompt), `conversation_id` (resume metadata only: `agent-session-resume.ts:280-283`) (`providers/cursor-tool-fields.ts:11-77`). Not read: `cwd`, `workspace_roots`, `generation_id`, `transcript_path`, `model`.

Cursor official event inventory [doc] https://cursor.com/docs/hooks: agent hooks `sessionStart, sessionEnd, preToolUse, postToolUse, postToolUseFailure, subagentStart, subagentStop, beforeShellExecution, afterShellExecution, beforeMCPExecution, afterMCPExecution, beforeReadFile, afterFileEdit, beforeSubmitPrompt, preCompact, stop, afterAgentResponse, afterAgentThought`; tab hooks; `workspaceOpen`. Common fields: `conversation_id, generation_id, model, model_id, model_params, hook_event_name, cursor_version, workspace_roots, user_email, transcript_path`. `postToolUseFailure` has `failure_type` (`error|timeout|permission_denied`) and `is_interrupt` - a `permission_denied` failure is the only post-hoc trace of a permission decision. `sessionStart` has `session_id, is_background_agent, composer_mode` and outputs `env`, `additional_context`. `stop` has `status` (`completed|aborted|error`), `loop_count`. matcher is a regex, "" or "*" = all; for `preToolUse` etc. matched against tool type (`Shell, Read, Write, Grep, Delete, Task, MCP:<tool_name>`).

cursor-agent (CLI) vs IDE: Orca only uses the CLI in a PTY (`RESUMABLE_TUI_AGENTS` contains `cursor`, resume = `cursor-agent --resume <conversation_id>`, `agent-resume-argv.ts:17-18`). Both share `~/.cursor/hooks.json`. [doc] the Cursor hooks page only says `workspaceOpen` "Runs in the Cursor desktop app and CLI"; it does not say whether the other hooks run in the CLI (OPEN-5). [inferred] Orca's own docs say "Cursor's TUI emits the state events Orca needs" (`docs/site/content/docs/agents/cursor-cli.mdx`), which implies hooks do fire in the CLI, but that page also says "full OSC state detection" while Orca's OSC matrix lists Cursor as NOT sending OSC 7501 (`src/main/agent-hooks/README.md:56`) - the docs page is inconsistent with the matrix.

Can a Cursor MCP server learn the conversation id? Findings:
- [doc] Cursor MCP docs (https://cursor.com/docs/context/mcp) say nothing about passing conversation/session ids, `_meta` or `clientInfo`. They document variable interpolation in `command, args, env, url, headers` of mcp.json: `${env:NAME}`, `${userHome}`, `${workspaceFolder}`, `${workspaceFolderBasename}`, `${pathSeparator}`; and list "roots" and "elicitation" as supported capabilities. Nothing per-conversation is interpolable.
- [secondary] Cursor forum feature request (22 May 2026) https://forum.cursor.com/t/mcp-tool-calls-should-include-composerid-in-meta-to-enable-per-conversation-server-side-state/161268 : an external MCP server "receives: _meta.progressToken only. No conversation identifier"; the composerId reaches the workbench's adapter and is dropped before the HTTP request; proposed `_meta["cursor/composerId"]`; no Cursor staff reply/fix visible. Related forum thread (https://forum.cursor.com/t/proposal-include-chat-tab-identifier-window-id-in-mcp-requests/121612): chat tabs in one Cursor instance share the same MCP `session_id`. A conference abstract (https://sessionize.com/s/shub-argha/we-reverse-engineered-every-mcp-clients-session-be/175279) reports Cursor shares "a pool of 6-8 sessions across all conversations". These cover HTTP MCP; for stdio MCP (child process) nothing was found.
- So: env, roots, clientInfo, `_meta` - none documented as carrying the conversation id. The only Cursor-side source of `conversation_id` is the hook payload. See section 8 for the hook-side correlation idea.

### 1.6 Codex: events Orca installs and the state machine

Events (`src/main/codex/codex-hook-definition.ts:21-31`) [read]: `SessionStart, UserPromptSubmit, PreToolUse, PermissionRequest, PostToolUse, SubagentStart, SubagentStop, Stop, Interrupt`. Comment: PermissionRequest "exits with no decision so Codex still shows its approval UI while Orca flips the pane to waiting"; `Interrupt` (Codex 0.150+) "is the only hook an Esc-cancelled turn fires; older Codex ignores the unknown key". Per-event timeout is clamped to Codex's cap (Interrupt 3 s) (`:64-73`). Not installed: `PostToolUseFailure` (not a Codex event), `PreCompact/PostCompact`, `SessionEnd`. Codex's docs list `SessionEnd` (main thread, reason currently always `other`, default timeout 1 s up to 3), `PreCompact/PostCompact` [doc] https://learn.chatgpt.com/docs/hooks (developers.openai.com/codex/hooks 308-redirects there).

Install mechanics [read]: `~/.orca/...` managed CODEX_HOME `hooks.json` plus real-home install (`codex-hook-definition.ts:33-35`, `codex-real-home-hook-install.ts`). Because "Non-managed hooks must be reviewed and trusted before they run" with trust recorded by hook hash [doc], Orca asks the Codex app-server for Codex's own hash of its entry (`src/main/codex/codex-hook-trust-derivation.ts:46-77`) and writes trust blocks into `config.toml` (`config-toml-hook-trust-edit.ts`); it also migrates the deprecated `[features] codex_hooks` flag to `hooks` (`config-toml-deprecated-hook-flag.ts`) [read]. [inferred] A Droidyard `init` that writes Codex hooks would hit this trust prompt (`/hooks` review) unless it replicates the hash derivation.

State machine (`src/shared/agent-hook-listener/providers/codex-events.ts:145-289`) [read]:
- SessionStart, UserPromptSubmit, PreToolUse (except request_user_input), PostToolUse -> `working` (:174-179).
- PermissionRequest -> `waiting`; PreToolUse with `request_user_input` (the AskUserQuestion-equivalent) -> `waiting` (:170-173, 180-181). Exception: if the turn's approvals are owned by Codex's auto-review agent (`approvals_reviewer = auto_review`), a PermissionRequest is downgraded to `working` because "the event alone is 'a decision is being made', not 'a human is blocked'" (:116-143, STA-7698).
- Stop and Interrupt -> `done`; Stop for a failed turn (rollout transcript shows failure) -> outcome `failure` (:260-265); a Stop is also synthesized for a root hook whose turn the rollout already recorded as ended (:291-314).
- SubagentStart/Stop and any payload with `agent_id` -> roster update, child-driven refresh (:88-114, 221-241).
- Ephemeral side chats (`transcript_path === null`, different `session_id`) are ignored so they cannot replace the pane's main turn (:158-168).
- Fields read: `session_id`, `transcript_path|transcriptPath`, `turn_id`, `agent_id`, `agent_type`, `model`, `source` (SessionStart; `compact` does not start a new turn), `tool_name|name`, `tool_input|input|arguments`, `last_assistant_message` (Stop), `prompt` (`codex-events.ts`, `providers/codex-tool-fields.ts:10-41`).
- Orca polls the Codex rollout for subagent state every 1000 ms (`CODEX_SUBAGENT_POLL_MS`, `src/main/agent-hooks/server/server-constants.ts:8`) [read].
- Codex official input fields [doc]: `session_id, transcript_path (string or null), cwd, hook_event_name, model`; turn-scoped add `turn_id`; PermissionRequest `tool_name, tool_input(.description)`; output `decision.behavior allow|deny`, "If no hook decides, the normal approval flow continues"; "Exit 0 with no output is treated as success". Default timeout 600 s (SessionEnd/Interrupt 1 s).
- Codex MCP and ids: [secondary] Codex sends `session_id` and `thread_id` in MCP `_meta` (https://sessionize.com/s/shub-argha/we-reverse-engineered-every-mcp-clients-session-be/175279) and a commit "Plumb MCP turn metadata through _meta (#15190)" adds `x-codex-turn-metadata` (https://forge.lthn.ai/core/core-agent-ide/commit/2bee37fe69fee6a8af13cd82850718433e8eb742, a mirror). Exact key names unconfirmed (OPEN-6).

## 2. Notifications in Orca

### 2.1 What triggers a notification

- **Done:** hook `done` (not `sessionBoundary`) -> `dispatchCompletion('hook', ...)`; if the agent had been seen `working` in the pane, it goes through the 1.5 s quiet window (`agent-completion-hook-observer.ts:138-196`, `agent-completion-notification-controller.ts:88-93, 236-266`). Also "title" and "process-exit" completion sources exist as fallbacks (`CompletionSource = 'hook' | 'title' | 'process-exit'`, controller:12). A Claude turn held `working` by background inventory announces the turn when its lead turn ended via the `turnCompletedAt` stamp (`agent-completion-hook-observer.ts:80-117`) [read].
- **Needs you:** hook `waiting` or `blocked` -> `dispatchAttention` (observer :48-50, 133-137): requires the pane to be live and have agent-run evidence, and dedupes per attention token so the same wait doesn't re-fire (`controller :219-234`; token = completion identity or `turn:state:agentType:toolName:toolInput:prompt`, :95-109) [read]. The notification text says "needs input" for `waiting|blocked`, "working" for working, "finished" for done+success/no verdict, "failed" for failure/interruption, "stopped" for cancellation/superseded/unconfirmed (`src/main/ipc/notification-options.ts:61-92`) [read]. Body = last assistant message (180 chars) else "Using <tool>: <input>".
- **Terminal bell** is a separate source (`terminal-bell`), "Bell in <worktree>" (`notification-options.ts:21-26`).
- Hook snapshots older than 10 s are not used to label a notification (`use-notification-dispatch.ts:36, 94-99`) [read].

### 2.2 Channels

1. **OS notification** via Electron `Notification` in main (`src/main/ipc/native-notification-delivery.ts:1-60`); macOS authorization checked first, `denied|not-determined` -> not delivered, renderer shows a fallback toast (`notification-delivery-service.ts:170-180`; `agent-attention-notification-delivery.ts:33-37`) [read].
2. **Sound:** played by the renderer only when the OS notification was `delivered` (`agent-attention-notification-delivery.ts:26-32`); sounds `system, two-tone, bong, thump, blip, sonar, blop, ding, clack, beep, custom` with volume (`notification-settings-types.ts:11-24`) [read].
3. **Dock badge (macOS):** unread count mirrored via `app.dock.setBadge`, `99+` cap (`src/main/dock/unread-badge.ts:5-12`; IPC `app:setUnreadDockBadgeCount`, `src/main/ipc/app.ts:195-196`); docs: "the same unread count is mirrored as a badge on the Dock icon" (`docs/site/content/docs/notifications.mdx`) [read].
4. **Tray attention dot** lit when a completion/bell arrives and the window is not visible, before any gate (`notification-delivery-service.ts:76-82`) [read].
5. **In-app unread + header bell + worktree chip** (`markAgentAttentionUnread`; unread is written before delivery so a suppressed banner still leaves a marker, `agent-attention-policy.ts:104-116`) and the **"Needs You" dashboard column** (section 1.1) [read].
6. **Mobile fan-out:** every request is also offered to paired phones, before desktop gating, even when desktop is focused or disabled (`notification-delivery-service.ts:96-133`), through a push gateway for a closed phone app (`src/main/runtime/push/push-dispatcher.ts:1-70`); agent state is mapped to `needs-input` (blocked/waiting) vs `finished`, and a `working` state sends nothing (`push-dispatcher.ts:47-58`); push can be limited to "only when desktop away" with away = system idle >= 180 s or locked (`desktop-away-state.ts:8-19`, `src/shared/desktop-away-threshold.ts:2`) [read].

### 2.3 Anti-spam

- Per-workspace desktop cooldown 5 s, keyed by `attentionKey ?? worktreeId ?? worktreeLabel ?? 'global'`; separate cooldown map for mobile; max 50 tracked keys (`src/shared/notification-burst-cooldown.ts:1-35`; `notification-delivery-service.ts:55-57, 152-164`). Comment: "agent-finish and terminal-bell often fire in one chunk; surface only the first" [read].
- `suppressWhenFocused` setting: no banner when the worktree is active and the window focused (`:142-150`).
- Attention token dedupe, 1.5 s hook-done quiet window, 1 s replay guard, `turnCompletedAt` pairing so a held turn is announced once (section 1.7).
- Machine/host mutes and a hidden-workspace mute (`mutedNotificationSourceIds`, `notifyHiddenWorkspaces`, `notification-settings-types.ts:26-28`; `agent-attention-policy.ts:62-65`) [read].
- Cursor `beforeShellExecution`/`beforeMCPExecution` are mapped to `working` specifically to avoid "waiting" notification spam (`cursor-events.ts:24`) [read].
- Codex PermissionRequest owned by the auto-review agent is not announced as "needs you" (`codex-events.ts:116-143`) [read].
- A `done` with `sessionBoundary` never notifies (observer :138-140).

### 2.4 Web/remote client

- The browser build's preload stubs notifications as unsupported: `dispatch` resolves `{delivered:false, reason:'not-supported'}`, permission `supported:false`, sound not played, and a comment "The browser client relays nothing to phones" (`src/renderer/src/web/preload-api/web-notifications-api.ts:4-16`) [read]. ## 3. OSC 7501 "Program Status Protocol"

Spec [doc] https://www.superlogical.com/rex/docs/build/program-status (revisions 0.1-0.4, 2026-09-28..10-10, per the page):
- Wire: `OSC 7501 ; key=value:key=value ST`; query `OSC 7501 ; ? ST`. Keys `[a-z]+`; values `[A-Za-z0-9_.,+/=-]*`; `msg` and `title` base64 UTF-8 without control chars. Unknown keys ignored; repeated key = last wins; malformed pairs skipped; a report breaking a limit is discarded whole.
- Keys: `state` (required: `idle|working|done|blocked|error`, or `clear`), `id` (slash path = parent/child records; absent = root), `kind` (only with `blocked`: `permission|question|auth`), `progress` (0-100, only `working|blocked`), `app` (<= 32 B, inherited by children), `title`, `msg` (one line).
- Handshake: terminal answers `?` and "may add `states` and `kinds` lists"; a program may send `CSI c` after the query to detect non-support without waiting.
- Lifetime: no heartbeat; on process exit or a new prompt (OSC 133 A) the terminal MUST drop `working` and `blocked` records (may drop `idle`); `done`/`error` survive; RIS clears all.
- Limits: 4096 B sequence; msg 2732 B enc/2048 dec; title 256/192; id 128 B, 32 per segment, 8 deep; 256 records (>= 64 required), LRU eviction.
- Reading: "The only bytes a terminal writes back are the feature detection reply ... there is no way to read records." The page does not address sidecars/multiplexers (it does not say a non-hosting process can read them).

Orca implementation [read]:
- Grammar/parser: `src/shared/program-status/protocol.ts` (prefix `\x1b]7501;` :4; states :10; kinds :13; limits :21-29; parse :117-189). Scanner reads the PTY stream, also tracks `\x1b]133;A` (prompt start -> `endProgram`) and `\x1bc` (RIS) (`osc-scanner.ts:13-17`).
- **Probe answer:** `\x1b]7501;?:states=idle,working,done,blocked,error:kinds=permission,question,auth\x1b\\` (`protocol.ts:18`). Sent by `installProgramStatusQueryResponder` on the terminal parser, "Answers `OSC 7501 ; ?` so Program Status Protocol programs (Claude Code, pi) start reporting" (`query-responder.ts:10-28`); skipped while replaying restored bytes. Also answered by main's hidden-pane emulator before the DA1 sentinel (query-responder.ts:11-14). A remote Orca host is answered only if it advertises capability `terminal.program-status.v1` (`protocol.ts:8`; README:64-71).
- Projection to Orca state (`agent-status-projector.ts:115-131`): working->working; blocked with kind permission|question -> `waiting`, otherwise `blocked`; done->done(success); error->done(failure); idle->done+sessionBoundary (or keeps an unseen done); a dropped root -> done+sessionBoundary. `app` ids map `claude-code`->`claude`, `grok-build`->`grok` (:19-22). `msg` becomes `toolInput` while live, `lastAssistantMessage` on done.
- Hook precedence: hooks win; OSC fills in when hooks are off/uninstalled/absent or silent >= 2 min on a differing state (README:11-26; `hook-precedence.ts`). A separate "facet" (`programStatus`) carries progress/msg/sign-in blocks beside the owning producer and never decides state (README:22-26).

Which clients emit it (Orca's matrix, "checked by running the real CLI in a PTY whose terminal answered queries the way Orca does", last updated 2026-10-17, `src/main/agent-hooks/README.md:28-71`) [read]:
- Claude Code: live-verified on 2.1.302, support since 2.1.295; probe required; all five states; kinds permission/question/auth; `msg` = task summary, "approve Write: ...", "answer: Q? (A . B)", errors; subagents as children; "Richest OSC 7501 of any harness, but no prompt and no session id".
- Grok 1.0.60 (`program_status = auto`), pi 1.3.0, oh-my-pi 18.10.3, Codex 0.163.0 (sends without asking; no `kind` sent; state only).
- Not emitting: OpenCode, Kilocode, **Cursor (installed binary 2026.06.02)**, Amp, Droid, Hermes, Muse, Devin, Kiro, Qoder, CodeBuddy, Jcode, Qwen, Gemini et al. (not checked).
- Side effect of answering the probe: **Claude stops putting its status glyph in the window title** once the probe is answered (README footnote 1:64-71), so Orca's title-based trackers switch to OSC activity.
- OSC 7501 cannot replace hooks for Orca: "no field for the prompt, tool input, assistant reply, model, or provider session id" (README:73-77).

Usable by a program that does not host the terminal (Droidyard)? [inferred, with the doc quotes above]: **No.** The records exist only in the PTY output stream between the agent and the terminal emulator that hosts it; the protocol offers no way to read them back (spec: "there is no way to read records"), and the agent only emits after the terminal answers the `?` probe (Claude: probe required). A daemon that is neither the terminal nor a PTY proxy never sees these bytes, and answering the probe is something only the terminal can do. Only if Droidyard interposed as a PTY host (e.g. launched the agent inside its own PTY) could it participate, which contradicts the "one daemon + MCP" scope. Do not plan on it.

## 6. Robustness of Orca's hook scripts

Common shape (Claude `src/main/claude/hook-script.ts:62-99`; Cursor `src/main/cursor/hook-script.ts:66-100`; Codex `src/main/codex/codex-hook-script.ts`) [read]:

1. **Canned stdout FIRST, before reading stdin.** Claude: `printf "{}\n"` (comment: "Claude-compatible permission hooks fail closed on empty stdout (#14818)", hook-script.ts:64-65; Windows `echo {}` :39-40). Cursor: prints an event-specific canned response from env `ORCA_CURSOR_HOOK_RESPONSE` else `{}` (:68-73), with comment "Cursor permission hooks fail closed on empty/invalid stdout (#15462)". Canned responses per event (`src/main/cursor/hook-events.ts:16-25`): `beforeSubmitPrompt {"continue":true}`, `stop {}`, `preToolUse {"permission":"allow"}`, `postToolUse {}`, `postToolUseFailure {}`, `beforeShellExecution {"permission":"allow"}`, `beforeMCPExecution {"permission":"allow"}`, `afterAgentResponse {}`. Because the answer is printed before any network work, a crash, timeout, or missing curl later still leaves a valid answer on stdout.
2. **Command wrapper with guard and fallback** (`src/main/agent-hooks/posix-hook-command.ts:8-33`): `if [ -f S ] && [ -r S ] && [ -x S ]; then ENV=... /bin/sh S; else printf '<canned>'; <drain stdin>; fi`. "Guard for a readable executable so a stale entry at a missing script becomes a silent no-op, not an exit-127 failure on every tool call"; "silence is a hard deny on gate events (Antigravity PreToolUse, #2426); those callers need the guard to still answer" (:7, :11). For Cursor the wrapper is `/bin/sh -c '<wrapper>'` because "Cursor uses the login shell" (`cursor/hook-script.ts:34`).
3. **stdin discipline** (`hook-stdin-contract.ts`): always consume stdin (`command -p cat`, stripped PATH must not cause exit 127 and EPIPE, #8110, :1-8); a Python JSON-stdin reader (5 s first-byte, 1.5 s idle) is used only for agents whose caller doesn't close stdin (Grok) (:10-102); empty payload -> `exit 0` (:105-119). On Windows the opposite rule: check Orca env BEFORE owning stdin and exit without reading, because abandoned stdin blocks forever (#11549, :173-203).
4. **Timeouts:** curl `--connect-timeout 0.5 --max-time 1.5` (`hook-post-command.ts:15, 25`; `installer-utils.ts` Windows variants; WSL fallback uses 3/5 s, `codex-hook-script.ts`); plus a host-level backstop `timeout: 10` in the client's config (`installer-utils.ts:46-49`; "independent of the curl --max-time", #4633). Transport on loopback `http://127.0.0.1:$ORCA_AGENT_HOOK_PORT/hook/<source>` with `X-Orca-Agent-Hook-Token`, `--noproxy 127.0.0.1`; POSIX sends the raw JSON body plus metadata in a base64 header (`X-Orca-Agent-Hook-Meta`, unit-separator-joined) when the endpoint advertises `ORCA_AGENT_HOOK_TRANSPORT=raw-json`, else form-encoded (`hook-post-command.ts:11-37`). Server side: 5 s slowloris cap (`listener-limits.ts:9`).
5. **Spool to disk when the server is down** (`hook-stdin-contract.ts:121-165`; `src/shared/agent-hook-spool.ts`) [read]:
   - On curl failure (`|| spool_hook_event`) or missing port/token/pane key, append a JSONL record to `<endpoint dir>/spool/pane-<last 36 chars of pane key>.jsonl` (dir 0700, file 0600): fields `paneKey, tabId, worktreeId, env, version, launchToken, source, receivedAt (ms), agentProcess, payload` (+ `hookEventName` for out-of-band-event agents).
   - Skips high-frequency progress events: `PreToolUse|PostToolUse|PostToolUseFailure` are never spooled (:141), so a replay can't flood.
   - Needs a readable endpoint file and a pane key, else returns without creating anything ("a stale env var must not create a spool tree for an Orca that is not installed here", :146).
   - Caps: 5 MiB per file (`wc -c` check, :157; `AGENT_HOOK_SPOOL_MAX_BYTES`), file truncated if older than 7 days (:154; `AGENT_HOOK_SPOOL_MAX_AGE_MS` 7 d), at most 1024 files replayed (`AGENT_HOOK_SPOOL_MAX_FILES`), records older than 7 d dropped on read (`readSpoolFile` :57-101).
   - Drain: on server start, before the listener binds; reads only complete lines (a torn trailing line is left for its writer), validates `paneKey/source/payload/receivedAt`, ingests with the stored launch-token hash check, then consumes the prefix in place (shift the unread tail forward and truncate, never unlink/replace the inode a writer may hold) (`agent-hook-spool.ts:103-160`).
6. **Endpoint file re-read after a restart:** `ORCA_AGENT_HOOK_ENDPOINT` points to `{userData}/agent-hooks/endpoint.env` (POSIX, `KEY=VALUE` lines) or `endpoint.cmd` (Windows, `set KEY=VALUE`), with `ORCA_AGENT_HOOK_PORT/TOKEN/ENV/VERSION` (+ transport); each hook sources it before posting: `if [ -n "$ORCA_AGENT_HOOK_ENDPOINT" ] && [ -r ... ]; then . "$ORCA_AGENT_HOOK_ENDPOINT" 2>/dev/null || :` ("refresh endpoint coordinates for PTYs surviving an Orca restart"; "suppress parse errors so they neither leak nor trip outer set -e") (`hook-script.ts:83-88`; parser `src/shared/agent-hook-endpoint-file.ts:16-41`; docs `hooks-memory.mdx` "Surviving a restart"). The Codex script parses the `.cmd` form line by line for WSL (`codex-hook-script.ts` `load_hook_endpoint`). Stale temp endpoint files are cleaned after 5 min (`agent-hook-endpoint-temp-cleanup.ts:5`). Version/env mismatches only warn once (`listener-limits.ts:53-`).
7. **Skip background-job processes:** `if [ -n "$CLAUDE_JOB_DIR" ]; then exit 0; fi` (POSIX) / `if not "%CLAUDE_JOB_DIR%"=="" exit /b 0` (Windows) (`hook-script.ts:24, 77-81`), because "a backgrounded session runs in a daemon worker that inherited the dispatching pane's env, so ORCA_PANE_KEY names a pane this session does not run in (#9236)". The Claude statusLine script has the same guard (`statusline-script.ts`). Caveat [secondary]: https://claudeissues.com/issue/59848 reports that after Claude Code 2.1.139 every session, including interactive ones, got a `$CLAUDE_JOB_DIR` pointing at a daemon-managed state directory (issue marked closed; I did not verify the current behavior), and no official page documents the variable (docs issue: https://claudeissues.com/issue/63040-docs-background-session-docs-omit-claude-job-dir-temp-file-behavior). A hook that exits on `CLAUDE_JOB_DIR` therefore risks muting interactive sessions on affected versions (OPEN-3).
8. **Other safety:** the Windows path uses `curl.exe` fully qualified under `%SystemRoot%\System32` so a repo-local curl.exe can't capture payloads (`installer-utils.ts` `buildWindowsAgentHookPostCommand`); the stdin reader uses `command -p` for the same reason (`hook-stdin-contract.ts:5-6`); the install sweeps stale/duplicate managed entries by script file name and preserves user hooks (`createManagedCommandMatcher`, `removeManagedCommands`, `installer-utils.ts:62-80, 160-`); the managed script is refreshed by content (`managed-hook-script-refresh.ts`).

Cursor "fail-closed on empty stdout" - confirmation against Cursor's docs [doc] https://cursor.com/docs/hooks: the docs say (a) exit 0 -> JSON used; exit 2 blocks; other non-zero exit/crash/timeout "fails open by default"; (b) for the permission hooks (`beforeShellExecution`, `beforeMCPExecution`, `beforeReadFile`, `beforeTabFileRead`, `subagentStart`, `preToolUse`) "invalid JSON or a response that doesn't match the schema blocks the action, even when `failClosed` is false"; (c) `failClosed:true` makes crashes, timeouts, non-zero exits and "no output" block. **The docs do not say how EMPTY stdout is handled for permission hooks without `failClosed`.** So Orca's "fail closed on empty" (#15462) is an Orca observation consistent with (b) if empty counts as invalid JSON, but it is not confirmed by Cursor's text. Also unresolved: whether `{}` (no `permission` key) satisfies a permission hook's schema - Orca avoids the question by always answering `{"permission":"allow"}` for the gate events (OPEN-4).

## 8. For Droidyard

Context used: `droidyard init` writes per-project hooks (Claude PreToolUse/PostToolUse/PostToolUseFailure on Bash and Write|Edit|NotebookEdit; Cursor beforeShellExecution, preToolUse Delete and Write, postToolUse/Failure); `droidyard hook` dials the daemon over a Unix socket within 2 s, fails open, answers Cursor with `{}`; sessions are MCP connections shown on `session.watch` with occupies/devices/stale; join by CLAUDE_CODE_SESSION_ID = hook `session_id`; MCP tool list budget 29,000 B with ~145 B left. Items are changes or decisions; each cites the finding.

1. **Print the canned answer first, before reading stdin or dialing.** Orca writes the answer line as the first action of the script (Claude `{}`; Cursor per event), so any later failure (daemon down, timeout, killed by the client) still leaves valid stdout (Cursor/Claude `hook-script.ts` quotes, section 6.1). In Go: write the response in the first statements of `main()` (or in a `defer`-proof wrapper). Change: `droidyard hook` must emit before `net.Dial`; keep the 2 s dial only for the report. [read]
2. **Do not answer Cursor permission hooks with bare `{}` until OPEN-4 is settled.** Orca answers `{"permission":"allow"}` for `beforeShellExecution`, `preToolUse`, `beforeMCPExecution` and `{"continue":true}` for `beforeSubmitPrompt` (`cursor/hook-events.ts:16-25`). Cursor docs: a permission hook's response that "doesn't match the schema blocks the action" (https://cursor.com/docs/hooks). Change: per-event canned map in `droidyard hook` for Cursor; run the OPEN-4 probe once. For `preToolUse` (Delete, Write) and `beforeShellExecution` use the allow object. [read + doc]
3. **Guard the hook command so a missing/moved binary is a silent no-op, and set an explicit `timeout`.** Orca wraps every command in `if [ -x S ]; then S; else <canned>; drain; fi` and writes `timeout: 10` per entry (`posix-hook-command.ts:8-33`, `installer-utils.ts:49`); client defaults are 600 s (Claude) and "platform default" (Cursor) [doc]. Change: `droidyard init` writes `"timeout": <small>` (e.g. 5) on every Claude/Cursor entry and wraps the command so that a deleted `droidyard` yields the canned answer instead of exit 127; `init` should also re-detect and sweep its own stale entries by binary name (Orca `createManagedCommandMatcher`). [read]
4. **Tighten the hook's own budget for the blocking path.** Orca uses `--connect-timeout 0.5 --max-time 1.5` (`hook-post-command.ts:15`); Droidyard's 2 s per PreToolUse is added to every Bash/Write call. Change: connect timeout ~0.5 s, whole report ~1.5 s for Pre events; since the answer is already printed (item 1), a slow daemon costs only latency, not behavior. [read + inferred]
5. **State model: add a `waiting` signal, but from the cheapest event.** Claude `PermissionRequest` (matcher can be restricted to the same tools: `Bash|Write|Edit|NotebookEdit`, plus an `AskUserQuestion` PreToolUse if wanted) -> mark the MCP session `waiting`; the next Pre/PostToolUse/PostToolUseFailure -> `working`; `Stop` -> `idle` (turn done; keep the session); `StopFailure` -> `idle` + failure note; `SessionEnd` with reason in {prompt_input_exit, logout, other} -> `ended`, but `clear`/`resume` -> keep and re-bind (Orca `CLAUDE_EXIT_SESSION_END_REASONS`, `agent-hook-listener.ts:33-38`). Value for Droidyard: a session that `occupies` a device while its agent is parked at a permission prompt for minutes is exactly the case `session.watch` `stale` should explain; this is the only place where Orca-style states help a device-lock runtime. The cost is one event name more per project in `init` and no MCP tool bytes. Version-gate new events (Claude < 2.1.100 discards the WHOLE settings.json on an unknown event, `claude-hook-event-versions.ts:5-23`): PermissionRequest >= 2.0.45, StopFailure >= 2.1.78, SessionEnd >= 1.0.85 (Orca installs only >= 2.1.261). [read + doc]
6. **Prefer `PermissionRequest` over `Notification` as the blocked signal; use `Notification` only as a stale-hint.** `Notification(permission_prompt)` arrives ~6 s late and resets on keystrokes; `idle_prompt` ~60 s after Stop [doc]; neither can block or answer. For a device lock the immediate PermissionRequest is better, and `idle_prompt` could drive the `stale` badge (agent finished 60 s ago, still holds a device). [doc + inferred]
7. **Cursor has no blocked signal.** Orca treats `beforeShellExecution`/`beforeMCPExecution` as `working` to avoid false "waiting" (`cursor-events.ts:24`). Droidyard should not show `waiting` for Cursor; show `working`/`idle` (stop) only, and use `postToolUseFailure.failure_type=permission_denied` as the only after-the-fact permission trace. [read + doc]
8. **Joining hook to MCP session: do not rely on a single key.** Orca joins by pane env, which Droidyard lacks. Risks and mitigations:
   - Claude: `CLAUDE_CODE_SESSION_ID` is fixed when the MCP stdio child is spawned (env is immutable), while `/clear` and interactive `/resume` issue a NEW `session_id` to hooks (SessionStart `source=clear`, SessionEnd `reason=clear|resume` [doc]) -> the join can silently go stale. Add a SessionStart hook (matcher `clear|resume|compact|startup`) to the project config: it reports (new `session_id`, `transcript_path`, `cwd`, and the agent's pid). Orca captures `ORCA_HOOK_AGENT_PID="${PPID}"` for exactly this kind of identification (`hook-process-capture.ts:1-3`). The daemon can re-bind by agent pid: the stdio MCP shim's parent pid is also Claude's pid. [inferred; verify OPEN-2]
   - Cursor: the conversation id exists only in hook payloads; MCP servers get nothing (docs silent; forum: `_meta.progressToken` only; tabs share a session). Most promising correlation, no MCP bytes: subscribe to `beforeMCPExecution` (Orca already does, `hook-events.ts:9`; fields `tool_name`, `tool_input`, `mcp_server_name` [doc]) filtered to the Droidyard server; the hook reports `(conversation_id, tool_name, hash(tool_input), t)` and the shim reports `(tool_name, hash(args), t)` for the call it receives; the daemon matches them inside a short window and caches `connection -> conversation_id`. Without it, fall back to `workspace_roots` (granularity: one Cursor window, ambiguous with two chats). Needs a spike (concurrency, tool_input equality). [inferred]
   - Never derive the transcript path from the session id (Claude's file name can differ from `session_id`, `agent-session-resume.ts:38-48`); store `transcript_path` from the payload.
9. **Do not add a session parameter to MCP tools.** Budget is 145 B; every identification need above is solved hook-side. The `additional_context` route (Cursor `sessionStart`, Claude SessionStart `additionalContext`) would tell the model its ID but costs model attention and tool-schema bytes for the parameter; the hook correlation costs neither. [inferred]
10. **Spooling: probably not, but copy the two cheap parts.** Orca spools to disk because its server can be down while agents keep running and its UI needs the final state. Droidyard fails open and its daemon is the source of truth for MCP connections (a missed Pre/Post event is harmless; `stale` is derived from the connection). Adopt only: (a) never spool progress events (Orca excludes Pre/PostToolUse, `hook-stdin-contract.ts:141`) - consistent with "no spool"; (b) if a lifecycle event (SessionStart/SessionEnd/Stop/PermissionRequest) must not be lost, keep a tiny append-only file with a size cap (Orca: 5 MiB, 7 days, 0600/0700) and drain on daemon start. Decide after item 5 lands: only lifecycle events are worth a spool. [read + inferred]
11. **Endpoint discovery after a daemon restart.** Orca hooks re-read a coordinates file on every call so PTYs outliving the app keep reporting (`hook-script.ts:83-88`). Droidyard's Unix socket path is stable, so it already has this property; if the socket path ever includes a per-run component, add an `endpoint` file and re-read it per invocation. Keep the socket mode 0600 and the dir 0700 (Orca spool dirs use the same). [read + inferred]
12. **Background-job skip: test before copying.** Orca skips hooks when `CLAUDE_JOB_DIR` is set because a backgrounded daemon worker inherits another pane's env. Droidyard has no pane env, but a background Claude session (`claude --bg`) will run its hooks against the same project config and could attribute events to the wrong MCP session if the join uses inherited `CLAUDE_CODE_SESSION_ID`. Check OPEN-3; if `CLAUDE_JOB_DIR` is also set for interactive sessions on the user's Claude, do NOT skip on it. [read + secondary]
13. **`stale` semantics.** Orca decays a non-`done` row after 30 min of silence (`AGENT_STATUS_STALE_AFTER_MS`) and treats a restored non-terminal row as never fresh (`restoredUnconfirmed`); it proves death by pid+start time rather than silence (`hook-process-capture.ts`). Droidyard has a better liveness signal (MCP connection closure). Change: define `stale` = connection alive AND last hook/tool activity older than N (for example the Orca 30 min), shown with the last known state (`waiting`/`working`), never auto-release `occupies` on hook silence alone; release on connection close or `SessionEnd` exit reasons. [read + inferred]
14. **Notifications (if Droidyard ever surfaces them in its web UI).** Do not plan for Web Notifications or web push: Orca's own web client has `dispatch -> not-supported` and no push (`web-notifications-api.ts`); only its native phone app gets push through a gateway. For Droidyard's web UI, in-page signals (title/badge/favicon, an in-UI "Needs you" list from `session.watch`) are the realistic channel. If desktop banners are ever added, copy: 5 s per-subject cooldown with an attention token so a repeat `waiting` doesn't re-fire (`notification-burst-cooldown.ts`, controller :95-109), a 1.5 s quiet window before announcing "done" so an immediate resume cancels it (controller :236-266), and "never announce `sessionBoundary` dones". [read]
15. **OSC 7501: out of scope for Droidyard.** It is readable only by the terminal host (spec: no way to read records; agent emits only after the terminal answers `?`), and answering it alters Claude's title glyphs. Droidyard does not host the terminal, so it cannot probe-answer or read it. Revisit only if Droidyard ever launches agents inside its own PTY. The hook channel (items 1-9) is the equivalent for a non-terminal runtime. [doc + read + inferred]
16. **Session history/resume: a read-only helper at most.** Orca's design shows what is cheap and stable: Claude `~/.claude/projects/<non-alnum-to-dash cwd>/<uuid>.jsonl` (+ `<uuid>/subagents/agent-*.jsonl`), Codex `~/.codex/sessions/**.jsonl` with `session_meta.payload.{id,cwd,git}`, Cursor `~/.cursor/projects/<slug>/agent-transcripts/<uuid>/<uuid>.jsonl` + `~/.cursor/chats/<md5(cwd)>/<uuid>/meta.json`. For Droidyard the only concrete use is to resolve a hook's `transcript_path`/`cwd` -> project, and to show a title; both come in the hook payload for free (Claude: `transcript_path`, `cwd`; Cursor: `workspace_roots`, `transcript_path`; Codex: `transcript_path`, `cwd`). No change recommended beyond storing those fields in the session record. Resume commands (`claude --resume <id>`, `codex resume <id>`, `cursor-agent --resume <conversation_id>`) are useful only if Droidyard offers "reopen the agent that held this device". [read]
17. **Hibernation and `orca worktree set --comment`: no direct equivalent needed.** Hibernation is memory reclamation of idle PTYs (needs a terminal host). The agent-written status line is the more transferable idea: a cheap, human-readable "what I am doing / blocked on" string per workspace. If Droidyard wants that, the cost is one MCP tool or one field on an existing tool (bytes!): given the 145 B budget, prefer reusing an existing tool's free-text argument (e.g. a `note`/`reason` field already present on the device-claiming tool) rather than a new tool. Orca puts no length limit on its comment (OPEN-9) - Droidyard should clamp (e.g. 280 chars) and strip control characters. [read + inferred]
18. **Codex hooks need trust.** If Droidyard `init` adds Codex hooks: Codex requires review/trust by hash (`/hooks`; changed hooks are skipped until re-trusted) [doc]; Orca had to derive Codex's hash through the app-server and write trust blocks (`codex-hook-trust-derivation.ts`). Recommendation: do not auto-install Codex hooks in v1; document the `/hooks` approval, or rely on Codex's MCP `_meta` (OPEN-6) for the join. [read + doc]
19. **Unknown-event hazard on install.** Orca encodes the fact that older Claude rejects the whole `settings.json` on an unknown hook name; Droidyard's per-project `.claude/settings.json` has the same blast radius. Change: gate every event added to `init` by the probed `claude --version` (as `getClaudeManagedHookPlan` does), and make `init`/doctor report the installed version vs. events written. [read]
